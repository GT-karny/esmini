## 2. 【項目1】静止摩擦 (breakaway) — 初期角度・方向・反復

`07_friction_map.py --part breakaway`。静止状態から力を 0.01 刻みで上げ、軸変位 >0.008 を「動いた」とする。各条件 2 回。

| 初期角度 | 左押し (力+) | 右押し (力−) |
| :--- | :--- | :--- |
| 0.00 | 0.170, 0.170 | 0.190, 0.200 |
| −0.15 | 0.210, 0.170 | 0.190, 0.190 |
| +0.15 | 0.170, 0.170 | 0.200, 0.190 |
| −0.35 | 0.190, 0.180 | 0.210, 0.200 |
| +0.35 | 0.170, 0.180 | 0.210, 0.200 |

* **breakaway = 0.170 〜 0.210**（FFB フルスケール比）。左平均 0.178 / 右平均 0.198。
* **方向非対称が実在**する（右の方が約 0.02 重い）。ただし試行間ばらつき（±0.02）と同程度なので、方向別の補償値を持つ価値はない。
* **初期角度依存は検出できない**。中央でも ±0.35 でも同じ範囲に収まる。→ **角度に依らない単一の定数で補償してよい**（重要: 補償を角度関数にする必要がない）。
* **0.16 以下では変位が厳密に 0.0000**。クリープもノイズ床もない。デッドゾーンは完全。

## 3. 【項目3】動摩擦・ヒステリシス・力→速度

### 3a. 静摩擦 vs 動摩擦（ヒステリシス帯）

`07_friction_map.py --part hysteresis`。静止から上げて動き出す力 (static) と、動いている状態から下げて止まる力 (kinetic)。

| 方向 | static | kinetic | ヒステリシス帯 |
| :--- | :--- | :--- | ---: |
| 左 | 0.17, 0.17 | 0.15, 0.15 | **0.02** |
| 右 | 0.20, 0.18 | 0.17, 0.16 | **0.02 〜 0.03** |

帯は狭い。一度動き出せば維持は容易で、**問題は「動き出せない」ことに尽きる**。

### 3b. 力 → 速度

`07_friction_map.py --part fv`。一定力を印加し、軸速度 [axis-frac/s] を実測。

| 力 | 左 v_late | 右 v_late |
| ---: | ---: | ---: |
| 0.16 | 0.000 | 0.000 |
| 0.22 | −0.234 | +0.182 |
| 0.28 | −0.417 | +0.345 |
| 0.34 | −0.641 | +0.564 |
| 0.40 | −0.797 | +0.778 |
| 0.46 | −0.841 | +0.827 |
| 0.52 | −0.892 | +0.893 |
| 0.58 | −0.950 | +0.954 |

* f ≲ 0.40 で線形: **v ≈ 3.35 · (|f| − 0.16)**。以降は飽和し **v_max ≈ 1.0 /s**。
* AD が要求する最大操舵レートは lc で約 0.05 /s、right_turn で約 0.6 /s。**力さえ出れば速度性能は十分足りている**（追従性の律速は速度ではなく静止摩擦）。
* この同定結果を `g29lib.WheelModel` に実装し、`09 --dry` で実機を使わないスクリーニングに使っている。

## 4. 【項目2】微小信号デッドバンド — 本件の核心

`08_smallsignal_deadband.py`。振幅 0.010〜0.150 のステップ目標を与え、①動くか ②追従できるか（末尾平均誤差 ≤0.010）を判定。左右両方向。

| 設定 | 動き出す最小振幅 | 追従できる最小振幅 | 残留誤差（全振幅） |
| :--- | ---: | ---: | ---: |
| **Kp=4.0（出荷値）** | **0.050** | **成立せず** | **0.030 〜 0.044** |
| Kp=8.0 | 0.035 | 0.050 | 0.006 〜 0.017 |
| Kp=4.0 + 摩擦FF 0.15 | **0.020** | **0.020** | 0.004 〜 0.010 |

**支配則が実測で確定した**:

> **デッドバンド ≈ F_break / Kp**

純 P サーボは誤差に比例する力しか出せないので、`F_break/Kp` より小さい誤差は原理的に静止摩擦を破れない。
出荷値 Kp=4.0 では **0.19/4.0 = 0.0475** → 実測 move_floor 0.050 と一致し、残留誤差も全振幅で 0.040 前後に張り付く（＝どの振幅でも「0.04 手前で止まる」）。

**lc の指令最大が 0.0648 で、96.2% が 0.035 以下**である以上、**出荷設定ではレーンチェンジのほぼ全区間でホイールは物理的に動けない**。ユーザー報告「ステアが一切動いていない」と完全に整合する。

**ゲインだけでは解けない**: 振幅 0.010 を追従するには Kp ≥ 0.19/0.010 = **19** が必要。Kp を 4→19 にするとトルク代理 override（閾値 |u|>0.20）が **1/5 の押し返しで発火**するようになり、これまで苦労して潰した誤検知が確実に再発する。→ **H3 単独は棄却**。

## 5. 【項目5】多成分干渉の再現 — 現行 C++ 合成の定量化

### 5a. 実機フィールドログとの一致検証

### 5b. 何が起きているか

`sat_predictive = -steering_pos * 1.5 * caster_onset` の `steering_pos` は **HVD のシミュレーション舵角**。
サーボの目標は「AD 指令 = そのシミュレーション舵角そのもの」なので、**AD が舵を切るほど SAT はその逆向きに立ち上がる**。両者は構造的に必ず対抗する。摩擦・ダンパも同じシミュレーション舵角の微分から来るので同様。

実測での対抗量（hands-off 再生時の feel 成分平均絶対値）: lc 0.015 / curve 0.055 / right_turn 0.093。
**breakaway が 0.19 しかない系で 0.05〜0.09 を差し引かれるのは致命的**。

### ここから読める非自明な事実

1. **出荷設定は right_turn ですら指令の 34% しか回さない。** 「動かない」は lc 固有ではなく全域の問題で、単に振幅が小さいほど顕在化するだけ。
2. **H1（SAT を物理軸由来に差し替える）だけでは 72% 止まり。** sat_reactive は `lat_accel` 由来で舵角の関数ではないため、ソースを差し替えても消えない。前任の本命仮説は**方向は正しいが単独では不十分**。
3. **潜在バグを発見**: **出荷設定は curve プロファイルの 28.6% の時間、誰も触っていないのに合成力が override 閾値 0.20 を超えている**（`fullOver`=0.286）。現状ホイールが動かないおかげで誤ラッチが顕在化していないだけで、**force 閾値だけを見る設計は既に危うい**。
4. **追従が良くなるほど誤検知圧力は下がる。** 追従できないと誤差が大きいまま → P 項が大きいまま。off+ff では `fbOver` が lc 0.010 / curve 0.008 まで落ちる。**「力を上げると誤検知が増える」は今回に限っては成り立たない**（後述の feedback-only 分離が前提）。

## 7. 【項目6】stiction 対策の比較評価

`10_stiction_methods.py`。同一条件（Kp=4.0 固定、振幅 0.010/0.020/0.035/0.065、左右）で 5 手法を実機比較。
`hold_ptp` は目標到達後に静止しているべき区間の軸振れ幅＝**ガタつき/ビビリの実測**。

| 手法 | 動き出す最小振幅 | 平均誤差 | 最大誤差 | hold 軸振れ | hold 平均\|u\| | hold u_std |
| :--- | ---: | ---: | ---: | ---: | ---: | ---: |
| none（出荷） | 0.065 | 0.0263 | 0.0410 | 0.0 | 0.167 | 0.0 |
| **ff**（クーロン摩擦フィードフォワード） | **0.020** | **0.0079** | **0.0099** | **0.0** | 0.123 | **0.0** |
| integrator (Ki=30, 寄与 clamp 0.25) | **0.010** | **0.0045** | **0.0060** | **0.0** | **0.053** | 0.0442 |
| dither (0.12 @ 30Hz) | 0.020 | 0.0159 | 0.0196 | 0.0022 | 0.093 | 0.0854 |
| punch (0.30 / 60ms) | 0.010 | 0.0066 | 0.0102 | **0.0261** | 0.056 | 0.0857 |

* **punch は棄却**: 追従自体は良いが、hold 区間で軸が 0.026 も揺れ、2.5 秒の試行中に 9 回発火する。ホイールが断続的に叩かれる＝ドライバーが触ったとき明らかに不快。
* **dither は棄却**: デッドバンド改善が中途半端（0.020）なうえ追従誤差が最悪（0.016）、かつ常時 u_std 0.085 の振動を出し続ける（可聴ノイズ）。
* **ff と integrator が残る**。両者とも hold 軸振れ 0（ガタつきなし）。
* 注目: **none の hold |u| が 0.167** で、override 閾値 0.20 まで **0.033 しか余裕がない**。追従できないせいで誤差が残り、P 項が出っぱなしになっている（§6-3 の潜在バグと同じ現象）。ff は 0.123、integrator は 0.053 まで下がる。

### ff と integrator の選択

| 観点 | ff | integrator |
| :--- | :--- | :--- |
| 微小振幅追従 | 0.020 から | 0.010 から（優） |
| 大信号 (right_turn) オーバーシュート | なし (99.5%) | +1.8% (101.8%) — 巻き上がり暴走はなし |
| 状態 | なし（誤差の純関数） | あり（activate/deactivate でリセット要） |
| ドライバーが握って対抗したとき | 0.15 で頭打ち | i_max=0.25 まで巻き上がって押し続ける |
| 物理的裏付け | 実測 F_kin=0.16 / F_break=0.17-0.21 に直接対応 | 経験的ゲイン |
| hold の指令リップル | 0.0 | u_std 0.044 |

**ff を推奨**。理由: (a) 実測した device 定数に一対一で対応するので他ホイールへの再校正手順が自明、(b) 無状態なので override ラッチとの相互作用がなく単体テストが純関数で書ける、(c) テイクオーバー時にサーボが「勝とうとしない」（上限が固定）。
integrator は僅差の次点で、将来 breakaway がもっと大きい機材が出たら追加検討でよい。

### ff の大きさ (fstat) の校正

`09_profile_replay.py --composite off --method ff --fstat <x>`（実機、lc/curve）:

| fstat | lc 誤差 | curve 誤差 |
| ---: | ---: | ---: |
| 0.10 | 0.0118 | 0.0144 |
| 0.13 | 0.0085 | 0.0115 |
| **0.15** | **0.0056** | **0.0092** |
| 0.17 | 0.0047 | 0.0081 |

0.15 で改善の大半が得られ、0.17 との差は僅か。

> **安全不変条件: `fstat < min(F_break)` を必ず守る。**
> 実測の最小 breakaway は **0.170**。fstat がこれ以上だと**摩擦補償だけでホイールが自走できてしまう**（誤差が微小でも動き出す＝暴走）。
> **fstat = 0.15** は最小 breakaway に対して 0.02 のマージンを残す。`10` の hold 試験で軸振れ 0.0（自走なし）を実測確認済み。

## 8. 【項目7】推奨設計と推奨値

### 8a. 二つの修正が両方必要（片方だけでは不足、実測済み）

| # | 修正 | 根拠 |
| :--- | :--- | :--- |
| **A** | target-track が active な間は **feel 成分（sat_predictive / sat_reactive / friction / damping）を抑制**する | §6: 出荷 28.8% → phys 差し替えでも 72% → 抑制で 93.5%。sat_reactive は舵角の関数でないのでソース差し替えでは消えない |
| **B** | サーボに **クーロン摩擦フィードフォワード** を追加: `u -= fstat * tanh(err / eps)` | §4: Kp=4 のデッドバンドは 0.0475 で lc 指令 (最大 0.065) をほぼ丸呑み。ゲインでは解けない (§4 末) |

**片方だけでは足りないことを実機で直接確認済み**（§6 の表、lc / curve の follow%）:

| 構成 | lc | curve |
| :--- | ---: | ---: |
| 出荷（A も B もなし） | 28.8% | 45.4% |
| **A のみ**（feel 抑制のみ） | 54.3% | 70.0% |
| **B のみ**（摩擦 FF のみ） | 70.8% | 67.7% |
| **A + B** | **93.5%** | **92.3%** |

さらに **B のみは curve で 30.3% の時間 override 閾値を超えたまま**（feel 成分が残っているため）＝誤ラッチ圧力が解消しない。A は追従だけでなく誤検知余裕のためにも要る。

### 8b. 推奨パラメータ

| 項目 | 値 | 根拠 |
| :--- | :--- | :--- |
| `target_track_kp` | **4.0（変更しない）** | override 閾値校正 (0.20 / 0.04) が Kp=4 前提。B で追従が解決するので上げる必要がない |
| `target_track_kd` | **0.35（変更しない）** | 同上。振動は観測されていない |
| `target_track_max_force` | **0.6（変更しない）** | right_turn で 99.5% 追従。飽和は起きるが不足していない |
| `target_track_friction_ff`（新規） | **0.15** | §7 校正。安全不変条件 `< min(F_break)=0.170` |
| `target_track_friction_ff_eps`（新規） | **0.01** | 誤差 0.02 で概ね飽和。これ未満だと微小誤差でのチャタリング寄り |
| `target_track_feel_ratio`（新規） | **0.0**（= active 中は feel 抑制） | §6。将来「AD 走行中も SAT を残したい」要求が出たら 0..1 で調整可能にしておく |

### 8c. C++ 実装時に必ず守ること（実測で判明した罠）

1. **override トルク代理には「フィードバック項のみ」を渡す**（`kp*err + kd*derr` のみ。摩擦 FF を含めない）。
   FF を含めると常時 0.15 の下駄を履き、閾値 0.20 まで 0.05 しか残らない。`g29lib.Servo.step()` が `(u, u_feedback)` の 2 値を返すのはこのため。実測で `fbOver` は lc 0.010 / curve 0.008 まで落ちる。
2. **soft_stop を feel 抑制に巻き込まない**。ハード端保護は安全機能。ただし現状の soft_stop は **シミュレーション舵角**で計算されており、守るべき物理ホイールの角度ではない（別件の実バグ。サーボ側 `hard_stop_zone` が物理軸で効いているので実害は出ていない）。
3. **H1 を「物理軸由来に差し替える」形で実装する場合の単位・符号の罠**: 引き継ぎ文書の案 `ReadPhysicalWheelNorm() * lock_angle_` は **スケールも符号も誤り**。
   正しい対応は `steering_pos[rad] = -steer_gain * norm`（`steer_gain=0.61`、`lock_angle=0.7` ではない、かつ **負号**）。
   ただし §8a A の結論は「抑制」なのでこの変換自体が不要になる。
4. **G29 の CONSTANT 符号**: 正の level → ホイール左 → 軸は負。Day-1 §1f のとおりで変化なし。
5. **方向非対称（右が 0.02 重い）に対する補償は不要**。試行間ばらつきと同オーダー。

### 8d. C++ 修正後に取るべき受け入れ実測（本研究で使った道具がそのまま使える）

* `09_profile_replay.py --composite off --method ff` の実測値が受け入れ基準の参照値になる: **lc follow ≥ 90% / 操舵中平均誤差 ≤ 0.010**、**curve follow ≥ 90%**、**right_turn follow ≥ 95%**。
* hands-off で `fbOver`（feedback-only 力が 0.20 超の時間割合）が **≤ 0.02** であること＝誤ラッチ余裕。
* 実 C++ 側では別途、実機 SDL2 経路で **軸を別プロセスで polling して実角度が動いたこと**を確認する（テレメトリの `tt` 非ゼロは動作の証拠にならない、が前回の教訓）。

## 8e. 実装後に実機で判明した追加事実（本研究の予測が外れて追い込めた分）

推奨設計を C++ に実装して実機計測したところ、**予測 92-94% に対し curve 76.9% / right_turn 53.0%** と大きく下振れした。
Python 再現では 91-99% 出ていたので、差分は「Python にはあって C++ にない/ない条件」にあるはず、として切り分けた結果:

### (1) G29 では CONSTANT と同時に SPRING/DAMPER を **走らせているだけ**で CONSTANT の実効力が落ちる

決定的だったログ: 製品側が `total=0.269` を **5 秒間連続印加しているのにホイールが 1 mm も動かない**。
実測 breakaway は 0.17-0.21、かつ §3b で 0.22 の一定力は 0.2 axis-frac/s で回すことを確認済みなので、**指令値が実効力として届いていない**と確定できた。

Python スパイクと製品の唯一の差は「製品は CONSTANT に加えて SPRING と DAMPER の effect も **生成して RunEffect している**」こと。
係数は 0 のまま（`emulate_via_constant_` 経路では更新されない）だが、DirectInput は複数 effect を合成し、デバイスの force budget を分け合う。
**F7b で SPRING に CARTESIAN direction 修正を入れた結果、それまで生成に失敗していた SPRING/DAMPER が成功するようになり、この副作用が有効化されていた**（Day-1 §1b/§3b の修正が、意図せず本問題を生んだ）。

対策: `target_track` 有効時は SPRING/DAMPER を**そもそも生成しない**（CONSTANT 単独チャネルにする）。実測は劇的:

| プロファイル | SPRING/DAMPER 走行中 | 生成しない | 本研究の予測 |
| :--- | ---: | ---: | ---: |
| lc | 98.5% (err 0.0107) | **109.0%** (err 0.0106) | 93.5% |
| curve | 76.9% (err 0.0250) | **92.4%** (err 0.0099) | 92.3% |
| right_turn | 53.0% (err 0.1210) | **99.4%** (err 0.0169) | 99.5% |

curve 92.4% vs 予測 92.3%、right_turn 99.4% vs 予測 99.5% と**予測値に一致**した。研究モデルは正しく、C++ 側に固有の減衰要因があっただけ。

### (2) サーボ更新レートは律速ではない（誤った仮説を実測で棄却）

製品の FFB は sim フレームごと（実測 28-40 Hz）で、研究は 250 Hz。最初これを原因と考えたが、
`09_profile_replay.py --loop-hz 28` で再計測すると **curve 91.3% / right_turn 99.1%** と 250 Hz とほぼ同じだった。
→ **更新レート仮説は棄却**。20-40 Hz でも一定力が保持されるので追従性は落ちない。

### (3) `cmake --build` は build 側 config をソースから再ステージする

実機設定（`input_type=sdl2_wheel` 等）を build 側に入れた状態でリビルドすると**黙って stub に戻る**。
これに気づかず 3 シナリオを計測して「全く動かない (follow 0%)」という偽の結果を得た（ログに `SDLFFBSink:` 行が 1 つも出ないのが判別点）。
**リビルド後は実機 config を入れ直す。**

## 9. やらなかったこと / 残課題

* **長時間連続 FFB**（30-60 分）での摩擦値のドリフト（発熱による変化）は未計測。
