## road.signal.validity.right_hand_traffic_lane_ids  [PARTIAL_DETERMINISTIC]
CHECK_LOGIC: For every <road> R (direct child of OpenDRIVE): road_rule = R.get('rule') or 'RHT'. This rule variant is active only when road_rule=='RHT'. For every <signal> S in R.find('signals').findall('signal'): orient = S.get('orientation'); skip if orient not in ('+','-'). Collect all <validity> children of S (S.findall('validity')); skip if none. For each validity v, parse fl=int(v.get('fromLane')), tl=int(v.get('toLane')) (skip malformed / fl>tl, that's a different rule's violation); lo,hi=min(fl,tl),max(fl,tl). Aggregate over ALL validity children of S: has_pos = True if any hi>=1 (a lane id >=1 -- 'positive/left' -- appears); has_neg = True if any lo<=-1 (a lane id <=-1 -- 'negative/right' -- appears). Lane id 0 (center lane) counts toward NEITHER has_pos nor has_neg (it is defined as neither positive nor negative by the lanes_numbered_correctly rule). expected = 'neg' if orient=='+' else 'pos' (RHT mapping). VIOLATION (flag road.signal.validity.right_hand_traffic_lane_ids) iff: (expected=='neg' and has_pos and not has_neg) or (expected=='pos' and has_neg and not has_pos) -- i.e. the signal's combined validity references real (non-zero) lane ids of ONLY the wrong sign, with no lane of the correct sign present anywhere among its own validity children. Do not flag when has_pos and has_neg are both True (validity genuinely spans real lanes on both sides) -- see ambiguity_source.
DO_NOT_IMPLEMENT (ambiguous residual, leave uncovered): The rule's second sentence ("if the given <validity> elements span both, positive and negative lane ids, @orientation='none' shall be used") implies that ANY signal whose combined validity spans real lane ids on both sides while orientation != 'none' is ALSO a violation. I re-scanned the full official+handauthored+resources .xodr corpus (via a standalone xml.etree script) and found this exact 'spans-both' pattern recurring -- not as noise, but with clean, round, apparently-deliberate bounds -- in: UC_Simple-X-Junction-TrafficLights.xodr (6 signals, validity=(-3,3), sign type 306 'Vorfahrtstrasse'/priority-road and type 1000001 traffic-light-related, on ordinary bidirectional roads with real driving lanes on both sides); UC_2Lane-RoundAbout-3Arms.xodr (2 signals, validity=(-3,4), sign type 283 'Halteverbot nach'/no-stopping); GT's own resources/xodr/fabriksgatan_traffic_lights.xodr and its _ctrl variant (4 signals total, validity=(-1,1), a real traffic-light signal); and resources/xodr/straight_500m_signs.xodr (a signal split into a (-3,-1) validity child and a (1,3) validity child under the SAME <signal id=0>, i.e. spans-both via multiple <validity> elements rather than one wide range). Unlike the sibling <object> rule (already implemented_gt, 0 hits on the official corpus per its own status_reason), the <signal> variant's spans-both pattern is both more frequent and recurs for specific, plausible-looking sign SEMANTIC categories (road-status / no-stopping / traffic-light) whose real-world legal effect could legitimately apply to the whole road cross-section regardless of which lane the physical board faces. Annex F defines no attribute (nor references any sign-type catalog) that would let a checker distinguish 'this <validity> is a literal per-lane restriction' from 'this <validity> is a whole-cross-section span for a road-level-status sign' -- so whether to flag these per the rule's literal second sentence, or treat them as a legitimate authoring idiom the text simply doesn't anticipate, is an interpretive/policy judgment the spec leaves open, not resolvable from XML structure alone.
