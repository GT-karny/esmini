# Implementation brief: add these rules to check_junctions_conn_crossing.py

## junctions.priority.no_signals  [PARTIAL_DETERMINISTIC]
CHECK_LOGIC: For every junction (type="default" or "virtual", both schema-legal parents of <priority> per OpenDRIVE_Junction.xsd) with >=1 <priority> child: (1) collect participating road IDs from connection/@incomingRoad, connection/@connectingRoad (and, for virtual junctions, @mainRoad); (2) for each such road id, look up <road id="..."> and inspect its <signals>/<signal> children; (3) if any such <signal> has @dynamic="yes", flag the junction -- a fixed/static <priority> ordering co-existing with a dynamically time-varying right-of-way device (e.g. a traffic light) is a direct logical-consistency conflict with the rationale given in 12.4.1, and this narrow condition is uncontested by any known corpus counter-example.
DO_NOT_IMPLEMENT (ambiguous residual, leave uncovered): Whether the rule's unqualified "signals" also covers static signs (the textually broader reading, supported by 14.1's definition and the related road.signal.priority rule) is not resolved by the checker-rule prose itself. Applying that broad reading as a hard structural test directly contradicts established, trusted GT authoring practice (static priority/yield signs routinely paired with an explicit <priority> element, since the sign's type code alone doesn't give a simulation engine machine-readable road-vs-road ordering). Resolving which scope was intended is a genuine interpretive judgment the spec leaves open; only the @dynamic="yes" sub-case is safely checkable.
