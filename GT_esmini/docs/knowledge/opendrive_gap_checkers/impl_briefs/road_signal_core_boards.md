## road.signal.dependency.multiple_dependency  [DETERMINISTIC]
CHECK_LOGIC: This is a permissive cardinality statement that is already fully and unconditionally granted by the XSD, not a prohibition. Algorithm: for every <signal> element (and, for completeness, every <staticBoard>/<vmsBoard> board sub-element) in the document, count(./dependency) may be any value 0..N -- there is no condition on that count, or on any other structural feature, that the rule text forbids. Consequently the deterministic checker is: iterate all <signal>/<staticBoard>/<vmsBoard> nodes, and PASS unconditionally regardless of dependency count -- no XML instance that is otherwise schema-valid can violate this specific rule (a violation would require the schema itself to cap count(./dependency) at 1, which it does not; maxOccurs='unbounded' at both occurrence sites confirms this). Note for the ledger: because no failing input is constructible, this rule has zero discriminating power as a lint check and should likely be marked 'not independently actionable / subsumed by XSD' rather than implemented as a real checker function, but the verdict per the requested taxonomy is DETERMINISTIC because the pass/fail algorithm (trivial as it is) is complete and fully derived from XML structure alone, confirming the prior pass's own reasoning was correct on the facts even though it filed this under 'gap_ambiguous'.

## road.signal.gantry.all_variable_boards_same_gantry  [PARTIAL_DETERMINISTIC]
CHECK_LOGIC: Checkable sub-case (structural precondition for the rule to even be evaluable, matching auditor suggestion part (a)): (1) Build a dict of signal_id -> <signal> element by collecting every <signal id="..."> under every <road>/<signals> in the document (xpath .//road/signals/signal). (2) Build a set has_vmsboard = {id for id,elem in dict if elem.find('vmsBoard') is not None}. (3) For every top-level <vmsGroup> child of <OpenDRIVE>, for every child <vmsBoardReference signalId="X">: flag a VIOLATION if X not in dict (dangling/unresolved signalId -- the referenced 'variable message board' does not exist) OR X in dict but X not in has_vmsboard (the referenced signal exists but has no <vmsBoard> child, i.e. it is not actually a variable message board and so cannot meaningfully 'belong to the same gantry' as a VMS group member). This is fully decidable from XML structure alone (element/attribute lookups only) and catches a real, common authoring defect (typo'd or stale signalId, or referencing a static-only signal), but it validates reference integrity and VMS-board-ness, not 'same gantry' itself -- see ambiguity_source for the uncovered part.
DO_NOT_IMPLEMENT (ambiguous residual, leave uncovered): The auditor's disputed suggestion had two parts; only the first is a genuine structural check. Part (b) -- 'referenced signals ... share the same (road id, s) within a small tolerance (a gantry = one road cross-section)' -- requires inventing a numeric proximity tolerance the spec never states, and treating 'same road + nearby s' as the definition of 'same gantry', which is an authoring convention, not a normative XSD/prose rule; a physically real gantry could legitimately have boards mounted with different s if the gantry structure spans a curve, and the 1.1 <reference elementType="object"> mechanism that COULD make the gantry link ID-exact is optional, free-text-typed, and absent from this repo's own reference fixture, so its presence cannot be assumed. Determining true gantry membership therefore requires either (i) geometric/tolerance judgment on s/t co-location that the spec leaves entirely open, or (ii) trusting an optional, semantically-unconstrained <reference> link whose use for this exact purpose is never mandated -- both are interpretive calls beyond pure XML structure.
