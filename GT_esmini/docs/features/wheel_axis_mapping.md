# feature:F8 — ハンコン軸割り当て設定（Wheel Axis Mapping）

> **状態**: 実装済（2026-08-06）。既定値は G29 レイアウト＝F8 以前のハードコードと同一なので、既存設定ファイルの挙動は不変。
> **関連**: [feature:F7](../../docs/tech_debt_audit_2026-06.md)（FFB / 介入検出）, `GT_esmini/config/manual_drive.json`, `GT_esmini/config/virtual_driver.json`

## 1. なぜ必要だったか

F8 以前、`SDL2WheelInput` は次の2つを**コード内に固定**していた。

- 軸の並び: `0=ステア, 1=スロットル, 2=ブレーキ, 3=クラッチ`
- ペダルの生値規約: G29 の「解放 = +32767 / 全踏み = -32768」

どちらも**デバイス側の事実**であってシミュレータの性質ではない。Logitech G923 は軸の並びが異なることが観測され、設定ファイルにそれを表現する手段が一つも無かったため、「ブレーキを踏むとクラッチが動く」状態を回避できなかった。

## 2. 設定キー

`manual_drive.json` の `input` ブロック（ボタン割り当てと同じ場所・同じ流儀）。

| キー | 既定 | 意味 |
| :--- | :--- | :--- |
| `steer_axis` | 0 | ステア軸 index。`-1` = 未割り当て |
| `steer_invert` | false | 正規化後に符号反転。**FFB の力の向きも同時に反転する**（§4） |
| `steer_raw_center` / `steer_raw_full` | 0 / 32767 | 中央 / 右フルロックの生値 |
| `throttle_axis` / `brake_axis` / `clutch_axis` | 1 / 2 / 3 | ペダル軸 index |
| `<pedal>_raw_released` / `<pedal>_raw_full` | 32767 / -32768 | 解放 / 全踏みの生値 |

VirtualDriver 側は `virtual_driver.json` の `sdl2_*` プレフィクス付き同名キー（VD も同じ `SDL2WheelInput` を使うため、片方だけ直すと VD 走行で誤読する）。

**ペダルに invert フラグは無い。** `raw_released > raw_full` が反転を意味する（G29 がこれ）。極性の表現を一つに限定してあるので、「二重に反転指定して自分と矛盾する」状態が作れない。

## 3. 軸番号の調べ方

```powershell
build\GT_esmini\Release\GT_WheelProbe.exe --list
build\GT_esmini\Release\GT_WheelProbe.exe --device 0 --hz 30
```

`GT_WheelProbe` は読み取り専用の SDL2 プローブで、JSON 行を stdout に流す。Web UI の「Axis Mapping」節（ManualDrive Settings パネル）はこれを裏で起動してライブバーを描き、「Detect」ボタンで動かした軸を割り当てつつ解放値／全踏み値も同時に校正する。

- **ブラウザの Gamepad API は軸には使わない。** ブラウザは独自の index 空間を持つため、「動かした軸を割り当てる」UI がシミュレータの読む番号とは違う番号を自信満々に書き込む。probe は実行時と同じ SDL・同じ index 空間で読む。
- probe の正規化値は**本番と同じ C++ 正規化器**（`WheelAxisMapping`）を通す。マッピングは CLI 引数で渡されるので、**保存前の編集中の値**もそのままプレビューできる。
- `GT_ENABLE_SDL2=ON` のビルドでのみ生成される（既定 OFF）。無い場合 API は 503 とその理由を返し、パネルは手打ち編集だけを提供する。
- **配布物に載せるには3か所を直す必要がある**: `build_package.ps1` の `--target` 列挙、同スクリプトのステージングコピー、`build_package.py` の `BIN_GLOBS`（exe は glob でなく1つずつ明示列挙）。忘れるとビルドは正常終了し警告も出ず、症状は「配布物で機能が無い」だけになる（初回パッケージで実際に踏んだ）。不在時の WARN を `check_prerequisites` に入れてある。

## 4. FFB の符号（安全上の注意）

`SDLFFBSink` の力の符号は軸の極性と結びついている（正の力 = ホイールを左へ = 生値が負方向）。軸が反転した機種で**読み戻しだけ直して力の符号を直さないと、F7 のターゲット追従サーボが目標から遠ざかる方向に押す＝正のフィードバックになる**。

そのため `steer_invert` は `SteerAxisSpec::SignFactor()` 1か所からのみ読み、

- 軸の読み戻し（`ReadPhysicalWheelNorm`）
- CONSTANT エフェクトの出力（`UpdateConstantEffect`）

の両方に同じ係数を掛ける。ユニットテスト `SteerInvertFlipsSignAndSignFactorAgrees` がこの一致を恒等式として固定している。方向を持つのは CONSTANT だけで、SPRING/DAMPER は大きさの係数なので反転不要。

反転設定を実機で初めて試すときは `ffb.safety_max_saturation_seconds` を有効にしてから走らせること。

### 4-1. なぜ 2 か所に掛けると打ち消えるのか（実機で確認済）

論理位置を `x = s·(a - c)/span`（`s` = SignFactor、`a` = 生値）、サーボ出力を論理力 `f`、デバイスへ出す力を `s·f` とする。デバイス力は生値を一方向へ動かす（`da/dt ∝ -s·f`）ので

```
dx/dt = s·(da/dt)/span ∝ -s²·f/span = -f/span
```

`s² = 1` なので**論理空間でのループ挙動は極性に依存しない**。だから「両方に同じ係数を掛ける」が正しく、片方だけだと符号が反転してループが発散する。

### 4-2. 実機での両極性確認（2026-08-06、G29）

`resources/xosc/verification/08_handoff/scenario_realwheel_vd_ffb.xosc`（VD が縦横とも保持しサーボが G29 を駆動する構成、ウォッチドッグ `|force| >= 0.570` が 2 秒で走行強制終了）で対照付き実施。

手順: ホイールを手で 90° 切る → 手を離す（MANUAL ラッチ・力が抜ける）→ △（`sdl2_auto_resume_button`=3）で AI へ返す → サーボがどちらへ駆動するかを見る。**AD 指令がほぼ 0 の直線路であることを利用している**（指令 0 なら「中央へ戻る／フルロックへ逃げる」が最大振幅の判別子になる。逆に指令が小さいと追従は目視できないので、追従の観察は判別子にならない）。

| 観測量 | A: `steer_invert=false` | B: `steer_invert=true` |
| :--- | ---: | ---: |
| 力が変位に逆らうサンプル（\|steer\|>0.10） | 38 | 11 |
| 力が変位と同方向 | 4 | 1 |
| 最大 \|steer\|（1.0 = フルロック） | 0.425 | 0.218 |
| ウォッチドッグ発火 | なし | なし |

両極性で収束＝§4-1 の不変性が実機で成立している。A の「同方向 4 件」は `force=-0.600`（飽和）で人が押している最中のサンプル。

**証拠の厚みの限定**: B は逸脱 12 サンプル・peak 0.218 で A（42 サンプル・0.425）より薄い。「逃げなかった・ウォッチドッグ不発火」は確実だが、統計量は同等ではない。

## 5. 非自明な事実（実測）

### 5-1. 静止しているデバイスは 1 バイトも送らない（＝全軸 0 は故障ではない）

2026-08-06、接続済み G29 で `GT_WheelProbe` が全4軸 raw=0 を返し続けた。独立計器（PySDL2）でも、SDL バックエンドヒント（HIDAPI / RAWINPUT / DirectInput）総当たりでも、`SDL_PumpEvents` 有無でも、video サブシステム＋ウィンドウありでも、HAPTIC を開いた構成（F7 の実測が取れた構成そのもの）でも同一だった。

**原因は「誰も触っていなかった」こと。** HID は状態変化時にのみ入力レポートを送るので、静止したホイールは何も送らず、SDL は開いた直後の 0 を返し続ける。実際、人が操作した 69 秒の記録では全4軸が即座に `reported: true` になった。`SDL2WheelInput` の解放センチネルのコメントが記述しているのと同じ条件で、**故障ではない**。

**教訓**: 「デバイスが壊れている / SDL の使い方が違う」と結論する前に、**入力が発生しているか**を確認する。列挙の成功（名前・軸数・ボタン数がすべて正しい）は、値が来ていることを何も保証しない。

G29 のペダル規約では raw=0 は正規化 0.4999…（≒半踏み）になる。したがって**正規化値だけを描くパネルは、何も言っていないホイールに対して「ペダルが半分踏まれている」と表示する**。これを防ぐため probe は各軸について「開始以降に一度でも非ゼロを報告したか」(`reported`) を返し、UI は未報告軸を `no report` と表示する。集計スクリプトも未報告フレームを統計から除外しなければならない（除外しないと raw=0 が「中間踏み」として min/max と静止値を汚す）。ランタイム側の同じ問題は F7 以前から「解放センチネル」で対処されている（§5-2）。

### 5-1b. 実機 G29 の実測レイアウト（2026-08-06、69秒の記録）

| 軸 | 操作区間 | min | max | 静止値 | 割り当て |
| :--- | :--- | ---: | ---: | ---: | :--- |
| a0 | 2–7s | -31082 | 32767 | -548 | ステア |
| a1 | 9–11s | -32768 | 32767 | 32767 | アクセル |
| a2 | 12–14s | -32768 | 32767 | 32767 | ブレーキ |
| a3 | 16–18s | -32768 | 32767 | 32767 | クラッチ |

出荷既定値（0/1/2/3・解放+32767・全踏み-32768）が実機で裏付けられた。軸の同定は「アクセル→ブレーキ→クラッチの順に踏んだ」という操作順と、軸ごとの活動区間の一致による。

**ブレーキの感触と実測は食い違う。** 操作者は「ブレーキは固くて踏み切れなかった」と報告したが、a2 は -32768（電気的下限）に 38 フレーム＝約1.9秒 留まっていた。G29 のブレーキはゴムストッパーで機械的には最後まで沈まないが、**センサーはその手前で飽和する**。校正を感触で決めてはいけない（浅く校正するとブレーキが過敏になる）。UI の Detect が「緊急ブレーキと同じ強さで踏め」と指示するのはこのため。

### 5-1bb. ペダルの極性が逆かどうかは、設定からは判定できない

**信号だけでは決まらない。** ペダル軸は 2 つの端の間を動く数でしかなく、どちらの端が「離した状態」かはデータと矛盾しない両方の解釈を許す。`raw_released > raw_full` を見て「反転している」と表示するのは**設定を読み上げているだけ**で、しかも正しい G29 でも真になる（解放が +32767）ため、逆に付いているペダルを「正常」と表示してしまう。判定器の形をした非判定器になる。

**判定できる観測はこれ**: ペダルは機械的に戻るので、誰も触っていない間に座っている生値が `raw_released` である。したがって

> **アイドル時（軸が静止している）の正規化値が ≈0 なら正常、≈1 なら端が逆**

軸が動いている間は判定不能（踏んだまま保持しているだけかもしれない）なので、UI は「一定フレーム以上変化していない」ことを確認してからのみ警告を出し、それ以外は黙る。Detect はこの前提を暗黙に使っている（検出開始時＝離している、という操作の意味づけ）。

**ステアには同じ検査が存在しない**（§5-1c）。FFB アイドル時のホイールは最後に置かれた位置に留まるので、静止値は何も意味しない。**同じ「静止値」がペダルでは基準値になり、ホイールでは基準値にならない** — この非対称が、ペダルの極性を機械判定できてステア中央を明示ボタンにせざるを得なかった理由の両方を説明する。

なお **ペダルに invert フラグは持たせない**（§2）。反転とは `raw_released`/`raw_full` の入れ替えそのものなので、UI は「Flip」ボタンでその入れ替えを提供する。フラグを併設すると同じ事実の表現が 2 つになり、互いに矛盾した状態が作れてしまう。

### 5-1c. ステアの「中央」は静止値から取ってはいけない

同じ記録で、ステア軸の静止値は -548 だった。**G29 は FFB がアイドルのときセンタリングばねを持たず、最後に置かれた位置に留まる**（ペダルは機械的に戻るので同じ問題が無い）。したがって「検出開始時の値を中央とする」設計は、たまたまホイールが向いていた方向を直進に焼き付け、手放しで一定の操舵バイアスを生む。

UI では Detect（軸＋右フルロックのみ）と「Set centre」（いま直進だと明示する）を分離してある。電源投入時に自己校正するホイールでは中央は 0 で、校正不要。

### 5-2. 解放センチネルは `raw_released != 0` の機種でしか成立しない

Windows/DirectInput は JoystickOpen 後しばらく raw=0 を返す。G29 ではこれが「半踏み」に見え、`OverrideManager` の throttle 閾値を踏んで縦方向が MANUAL にラッチしてしまう（F7 で対処済）。F8 でこのセンチネルは軸ごとの `raw_released` に一般化したが、**`raw_released == 0` の機種ではガードを無効化しなければならない**。その機種では raw=0 が正しい「解放」であり、センチネルを効かせると raw=0 が永久に「未報告」と判定されてペダルが死ぬ。

### 5-3. 既定値の回帰は「0.5」ではない

旧 `NormalizePedal` は `(32767 - raw) / 65535` なので raw=0 は **0.49999237**。ユニットテストで 0.5 を期待すると、実装が旧挙動を正しく再現していても落ちる（実際に一度落ちた）。「挙動不変」の主張は旧式そのものに対して書くこと。

### 5-3b. 正規化 0 は -0 になり得る

`(32767 - 32767) / -65535` は IEEE 754 で **-0.0**。値としては 0 と等しいが `"-0"` と直列化され `"-0.00"` と表示されるので、解放されたペダルが負値として出た（実機で観測）。`WheelAxisMapping` 側で符号を落としてある（表示側で潰すと、テレメトリや将来の符号判定に -0 が漏れる）。`EXPECT_DOUBLE_EQ(v, 0.0)` は -0.0 でも通るため、テストは `std::signbit` で書く。

### 5-4. `GT_WheelProbe` は SDL2main を使わない

Windows では `SDL.h` が `main` を `SDL_main` に置換するため、素の console ツールは `SDL_MAIN_HANDLED` + `SDL_SetMainReady()` を使う。SDL2main をリンクすると WinMain 経路を引き込む。

### 5-5. probe が CommonMini を引かない理由

esmini のロガーは既定で stdout に書く。probe の stdout は web backend が読む JSON ストリームなので、ログ 1 行で壊れる（加えて起動場所に log.txt を作る）。だから probe は `CommonMini` も `ManualDriveConfig` もリンクせず、`WheelAxisMapping.cpp` だけを直接コンパイルする。
