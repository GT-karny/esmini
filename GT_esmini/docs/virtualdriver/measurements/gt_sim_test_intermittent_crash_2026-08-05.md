# gt_sim_test batch: 断続的なネイティブクラッシュ（car_following_traffic_control）

**日付**: 2026-08-05 · **状態**: 既知の欠陥として記録（是正は本文書の射程外）
**発見の経緯**: ManualDrive-ADAS フェーズA検証作業（req-vd-ad:REQ-AD-025/028）に付随して
回帰バッチを繰り返し実行していた際に発見。**この欠陥自体は当該作業に起因しない**
（下記「帰属」参照）。この文書はその作業の一部としてではなく、独立した既知欠陥の記録として書く。

## 1. 観測事実

`resources/xosc/verification/car_following_traffic_control_batch.yaml` を
`DriverScript/.venv/Scripts/python.exe GT_esmini/scripts/verification/gt_sim_test.py batch <manifest>`
で**繰り返し**実行すると、断続的にネイティブクラッシュ（`access violation`）が発生する。

- **頻度**: 5 回中 2 回（同一マニフェスト・同一ビルドを 5 回連続実行）。
- **再現するシナリオ・フォールトアドレスは毎回異なる**: 2 回のクラッシュはそれぞれ別のシナリオで発生し、
  フォールトアドレスも `0x0` と `0xFFFFFFFFFFFFFFFF` で異なった。
- **この不安定さのパターンはダングリングポインタの指紋であり、単純な null 参照ではない**——
  null 参照なら毎回同じアドレス（`0x0`近辺）・同じ経路で再現するはずだが、本件はアドレスも
  発生シナリオも走行ごとに変わる。これは典型的な「解放済みメモリを指すポインタを後から踏む」
  型の不定動作と整合する。

## 2. 再現レシピ

**1 回の実行では見えない。バッチを繰り返し回すことが再現の必要条件。**

```powershell
DriverScript/.venv/Scripts/python.exe GT_esmini/scripts/verification/gt_sim_test.py batch `
    resources/xosc/verification/car_following_traffic_control_batch.yaml `
    --out test_results/<出力先> 
# 上記を 5 回程度連続で実行し、access violation の有無と発生シナリオ・フォールトアドレスを記録する
```

1 回だけ流して「緑だった」と結論しないこと——本件の発生率（5回中2回）は単発実行では高確率で見逃す。

## 3. 単独では再現しない（本リポジトリの既存規律どおり）

同じシナリオ単体を切り出して 2 回連続実行したところ、**2/2 ともクリーンだった**（クラッシュ再現せず）。
これは本リポジトリで既に定着している規律——**「バッチ失敗は単独再確認が必須」**
（`GT_esmini/docs/knowledge/signal_catalog.yaml` の関連コメント、および過去の連鎖クラッシュ切り分け作業
で踏襲された手順）——に従った結果であり、その規律が今回も機能したことの一例でもある。
単独では再現しないという事実は「クラッシュが存在しない」ことの証明ではなく、**バッチ実行に固有の
何か**（実行順序・複数シナリオにまたがる状態の持ち越し・メモリ再利用のタイミング等）が引き金に
関与していることを示唆する。

## 4. 帰属（本作業に起因するかどうかは測定で決着済み）

**方法**: 同一バッチ（`car_following_traffic_control_batch.yaml`）を、本セッション開始時点の
DLL（`dist/GT_Sim_v0.14.3/bin/GT_esminiLib.dll`、バイト来歴が本セッションの開始点ビルドと一致する
既知の旧バイナリ）に対しても 5 回連続実行した。

**結果**: 旧 DLL でも **5 回中 2 回**、同じ signature（access violation、シナリオ・アドレスが
毎回異なる）で再現した。

**結論**: このクラッシュは**本セッションの変更（ManualDrive-ADAS フェーズA）以前から存在する**
既知欠陥である。1 回でも旧バイナリで再現すれば既存であることの証明として十分であり、これは
その基準を満たしている。

**結論として言えないこと（正確を期すため明記）**: 発生**率**が本作業の前後で変化していないかは、
**各腕 n=5 では判定できない**。5 回中 2 回という観測は分散が大きく、真の発生率が本作業の前後で
（例えば）10% から 40% に変わっていたとしても、この n では区別できない。**「発生率は不変」と
主張しない**——主張できるのは「本作業以前から存在する」という存在の証明のみである。

## 5. この欠陥をどう扱うか

- 本文書は**記録のみ**。是正（原因調査・修正）は別作業のスコープ。
- GitHub Issue は起票していない（起票はユーザー確認後の対外的アクションであり、この作業の範囲外）。
- ManualDrive-ADAS フェーズA（req-vd-ad:REQ-AD-025/028）の作業成果・matcher 実測・KG 記帳は、
  本欠陥の存在に関わらず有効である（本欠陥は `car_following_traffic_control_batch.yaml` 側の
  話であり、`manualdrive_adas_batch.yaml` の実測（`test_results/mdadas_run3`）とは独立）。
- 発生率を確定させたい場合は n を増やす（両腕とも最低 20 回程度を推奨——5回では検出力が低い）。
