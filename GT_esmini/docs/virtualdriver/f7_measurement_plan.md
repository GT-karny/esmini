### 用語

* **測定量 (measurand)**: 判断に直接使う量。`M-xx`。
* **器具 (instrument)**: 測定量を生む道具の連鎖全体（テレメトリ出力 → 生成スクリプト → 分析スクリプト → 集計）。`I-xx`。
* **検定 (verification)**: 器具が正しい値を返すことを、**測定の前に**独立に確かめる手続き。`V-xx`。
* **計測連鎖 (chain)**: 測定量が通る器具の並び。§4。

## 2. 残っている判断と、判断に必要な測定量

判断は 5 件。各判断について「判定規則」を先に固定する。**判定規則を後から動かさない。**

### J1 — 介入検出しきい値の水準決定（`residual_threshold`、現行 0.08）

**判断文**: `residual_threshold` を現行 0.08 のままにするか、下げるか、上げるか。

**判定規則**:
```
下限 = max( 検出下限 0.01729 ,  手放し残差の worst × 安全率 k )
上限 = 拾うと決めた最小介入が到達する residual の min
採用値は [下限, 上限] の中で、下限側に安全率を残した位置に置く。
区間が空なら「この方式ではその要求を満たせない」と結論する（しきい値をいじって辻褄を合わせない）。
```
安全率 k は**測定の前に**固定する（本計画では **k = 1.4**、根拠は §2 末尾）。

**必要な測定量**:

| ID | 測定量 | なぜ要るか |
| :--- | :--- | :--- |
| **M-01** | 手放し走行の `residual` **最大値**（走行ごと・シナリオごと・config ごと） | 下限を決める。平均・p50 は使わない（p50 は 0.0001-0.0003 で判断に無関係） |
| **M-02** | M-01 の**走行間 worst と spread**（反復 N 回） | D-6。単発では +50% 振れる |
| **M-03** | 手放し走行の `sustain_accum` 最大値 | 発火への到達率。0 でない＝発火の一歩手前 |
| **M-04** | 手放し走行の **MANUAL ラッチ件数**（整数） | 誤検知の直接の真値。連続量より頑健 |
| **M-05** | 介入 4 象限 (a) 内側で押さえる / (b) 追い越す / (c) 逆へ切る / (d) 握って動かさない、各々が到達する `residual` の**最小値** | 上限を決める。象限ごとに構造的に差があるので**象限別に**要る |
| **M-06** | 検出下限 x（`kp·x + friction_ff·tanh(x/eps) = breakaway` の解） | ハードウェアが決める床。しきい値をこれ以下に下げても意味がない |

**必要十分性**: 下限は M-01/M-02/M-04、上限は M-05、床は M-06 で決まる。
**要らないもの**: 躍度分布・kappa・軌跡偏差は J1 に**一切関係しない**。測るなら別の判断のために測ること。

### J2 — シャドウモデルの実機妥当性

**判断文**: シャドウ（力から予測したホイール位置）は、実機の物理ホイールを妥当に代表しているか。

**注意**: 「残差がしきい値を下回った」は妥当性の証明ではない。それは**結果**であって、
**予測が当たっているか**とは別である。しきい値が緩ければ、外れているのに下回る。

**判定規則**:
```
(1) 帯の外（|f| < 0.170 または |f| > 0.210）で、shadow_moving と物理ホイールの実際の運動が一致すること。
(2) 残差が系統的な偏り（片側に伸び続ける）を示さないこと。
(3) 実機マージン worst が目標水準（新① = 2.0x）以上であること。
(4) 上記を、同定に使っていない別セッションの走行で示すこと（D-7）。
いずれか一つでも欠けたら「妥当性は未証明」と書く。合成でどれだけ通っても書かない。
```

**必要な測定量**:

| ID | 測定量 | なぜ要るか |
| :--- | :--- | :--- |
| **M-10** | `shadow_moving` と**物理ホイールの実運動**の一致行列（真陽性/偽陽性/偽陰性） | 妥当性の本体。**「残差が小さい」では代替できない** |
| **M-11** | breakaway 帯（0.170-0.210）の滞在時間割合 | 帯の内側ではシャドウ第2アームが実測を読むので**証拠として弱い**。弱い証拠が全体の何割かを定量する |
| **M-12** | 帯の外に限定した M-10 と残差最大 | (1) の判定に使う |
| **M-13** | 実機マージン = `residual_threshold / residual_max`、区間別（moving / stationary / ALL）、N 反復の worst | (3) の判定 |
| **M-14** | 残差の符号付き偏差 `actual_norm − shadow_norm` の時間平均とドリフト率 | (2) 系統偏りの検出。絶対値だけでは偏りが見えない |

**必要十分性**: M-10/M-12 が本体、M-11 が証拠の強度、M-13 が水準、M-14 が偏り。
**M-13 単独では判断できない** — 現在この 1 つしか無いのが J2 の未証明の理由。

### J4 — 車線 1 本分の横ずれからの復帰の乗り味

**判断文**: 車線 1 本分（約 3.5 m）の横ずれから復帰するとき、躍度上限は乗り味を改善するか。

**この判断は現在ブロックされている。** 条件を作るハーネスが、**基準が途中で張り替わる量を制御目標にしている**
（§6 T8）。条件が成立していたかどうかが分からないので、その上で測った乗り味も判断に使えない。

**判定規則**:
```
前提: 条件成立の証明が先。
  (P1) 横ずれ量が目標値に到達したことを、基準が張り替わらない量で示す
  (P2) 車両が走行車線の外へ出ていないことを、生の lane id 系列で示す
  (P3) ルート逸脱が起きていないことを示す
P1-P3 が揃って初めて乗り味の数値を読む。
乗り味:
  立ち上がり躍度が上限値どおりに抑えられ、かつ

```

| ID | 測定量 | なぜ要るか |
| :--- | :--- | :--- |
| **M-30** | **横ずれ量（基準が張り替わらない量で）** | P1。`ego.offset` は使用禁止（§6 T8）。代替は §4.4 |
| **M-31** | 走行中の**生の `lane` id 系列**（値そのもの。真偽値に潰さない） | P2。現状ハーネスは成功時に `departed` の真偽値しか印字しない |

### J5 — 有人での最終確認

**判断文**: 人がホイールを握って、要求どおりに動くことを確認できるか。

**構造的制約（監査の指摘）**: 無人で取れるのは「手放しで誤発火しないこと」だけ。
**検出側 (a)(b)(c)(d)・複数サイクル・官能は、原理的に人がホイールを握らないと取れない。**

**設計原則**: **人には人にしか出せないものだけを出させる。**
数値は全部ログから事後に取る。走行中に画面の数値を読ませない（監査指摘 #2/#3）。

| ID | 測定量 | 誰が出すか | 取得方法 |
| :--- | :--- | :--- | :--- |
| **M-40** | 象限 (a)(b)(c)(d) の**介入操作そのもの** | 人 | 人の手。操作の開始・終了時刻をボタン/マーカーで記録する |
| **M-41** | 各象限で**ラッチしたか**（真偽）と、そのときの `residual` 時系列 | ログ | 事後にログから。**目視しない** |
| **M-42** | 複数サイクル（介入→RESUME→再介入 ×3）の**各サイクルのラッチ成否** | ログ | 事後。RESUME 押下は `resume_pressed` に出る |
| **M-43** | B-1b「隣車線へずらしてから復帰」の主観評価（低速側・高速側の 2 回） | 人 | **事前に定義した尺度**で。自由記述は補足に留める |
| **M-44** | 官能（取られ・バイアスの不快さ・ラッチ瞬間の暴れ） | 人 | 同上 |

**M-43/M-44 の尺度は走行前に固定する。** 走ってから尺度を作ると、結果に合わせた尺度になる。

**現行ランブックの状態**: 監査が指摘した「走行中に読めない指示」「目視でしか取れない判定基準」は
**解消済み**。判定は `wheel_session_report.py` の `find_episodes()` / `classify()` が事後に機械判定し、
人から受け取るのは B-2 の所感だけ、とランブックに明記されている。

> **安全上の申し送り**: 安全ハーネス S1-S5 は実装がコード上正しいことを確認済みだが、
> **実機 15 走行で一度も発火しておらず、実際に効くという一次証拠が無い。**
> 有人パートは人がホイールを握る＝S1/S2 が発火しうる唯一の場面である。
> **有人走行の前に、S1-S5 を意図的に発火させる試験（陰性対照ではなく陽性対照）を 1 回行うこと。**
> 歯止めが効くことを確かめずに人を座らせない。

### 安全率 k = 1.4 の根拠（測定前の固定）

実機の走行間 spread が実測 +42〜50%（`residual` max が 0.0377→0.0566 等）。
1 回の走行で観測した worst は、次の走行で最大 1.5 倍程度まで伸びうる。
k = 1.4 は「観測 worst の 1.4 倍まで来ても発火しない」を要求する。
**これは仮の値であり、N を増やして spread の分布が分かれば置き換える。**
置き換えるときは「結果が気に入らないから」ではなく「N が増えたから」を理由にすること。

### 4.2 3 つの時刻断面（**最重要**）

**1 行の JSONL に 3 つの異なる瞬間が同居する。**

| 断面 | フィールド | 中身 |
| :--- | :--- | :--- |
| **① pre**（物理積分の前 = 前フレーム末の姿勢 `dstate`） | `driver.*`, `envelope.*`（`steer_in`/`steer_out`/全 `*_active`）, `preview.*`, `midlong.*`, `policy.*` | AD が「今フレーム何をするか決めた」ときの状態 |
| **② post**（このフレームの物理積分の後） | `ego.*`, `front_bumper.*`, `ffb.*`（トップレベル） | 積分結果 |
| **③ 1 フレーム遅れ**（**前の行**の `ffb.*` そのもの） | `ffb.gates.*` 全部 | `override_mgr_.UpdateFfbSample()` が Step 冒頭で前フレームの FFB サンプルを読むため |

**恒等式（検定に使う）**:
```
gates.actual_norm(N)  ==  ( ffb.target_norm − ffb.position_error )(N−1)      … 厳密
```
**静止中は N と N−1 が同値なので、この式は静止中には成立して見える。**
動作中の区間で確かめないと意味がない（§5 V5）。

**①と②の食い違い**: 包絡線は `dstate.speed`（前フレーム積分後）で判断するが、`ego.speed` は
このフレームの積分後。**加減速中は系統的にずれる。定速では一致して見える。**
これが撤回された kappa 比 1.0078 の直接原因。

#### ★ dt の宣言値と実測値の 5 倍乖離（**本計画で新たに発見。既報告 8 件に含まれない**）

実機走行の一次記録において、**CLI が宣言する dt と、テレメトリが実際に刻む dt が 5 倍違う**。

```
supervisor:  GT_Sim.exe ... --fixed_timestep 0.05          （supervisor_right_turn.log:1）
esmini:      "Run simulation decoupled from realtime, with fixed timestep: 0.05"
             （f7_realwheel_right_turn.log:12）
テレメトリ:   sim_time = 0.010000000, 0.020000000, 0.029999999, ...   ← 1 行あたり 0.01
```

凍結セット（16:16）と再走行セット（23:16）の**両方**で同じ。つまり実機の一次記録は
**すべてこの乖離の下で取られている**。

**影響**: CLI 値（0.05）を dt として微分すると、**レートは 5 倍、躍度は 25 倍ずれる。**
`sim_time` 差分（0.01）を使えば正しい。既存文書の「実機の dt は 0.01」という記述は
**結果として正しいが、CLI 引数はそれを裏切っている。**

> **規則 — dt は必ず `sim_time` の連続差分から実測すること。**
> **CLI 引数・config・スクリプト内の定数から取ってはならない。**
> 差分が一定でない場合はフレームごとの dt を使い、一定性そのものを報告に載せる。

**機構（ほぼ特定済み・1 点だけ要確認）**: **二重クロック**である。
`f7_realwheel_basic.log:49` に `SDL2WheelInput: ... Running at 100.0 Hz (realtime pacing: ON)` とあり、
**シナリオは 20 Hz を宣言、ホイール入力／テレメトリ経路は 100 Hz** で回っている。
`11_rig_followcheck.py:71-74` のコメントが一般論として既にこの現象を認識している
（"the telemetry frame rate is not necessarily 1 per requested step"）。

> **要確認（調査者間で証言が割れている）**: 一方の調査は「`manualdrive/` 配下に独立した
> 高頻度スレッド（`std::thread` / `SDL_AddTimer`）は存在せず、FFB は `Step()` 内で 1 回だけ回る」
> とコード検索で結論した。他方は上記のログ行を実データで示した。
> テレメトリ捕捉が `GT_Step()` から毎回呼ばれる以上、**テレメトリ行数 = `GT_Step()` 呼び出し回数**
> であり、行が 0.01 刻みなら `GT_Step()` は 0.01 で刻まれている＝`--fixed_timestep 0.05` が
> **効いていない**ことになる。**どちらが正しいかを 1 度だけ確認すること**（排他解除後）。
> **確認の結果に関わらず、上の規則（`sim_time` 差分を使う）は安全側で変わらない。**

**既存コードの状況（良い知らせ）**: 分析側は既に 0.01 へ収斂している。
`residual_vs_jerkcap.py` の `REAL_MACHINE_DT=0.01`（「実機 3 走行すべて実測 dt=0.01」というコメント付き）、
`resume_ride_feel.py` の dt 既定 0.01 化はいずれもこの実測に基づく。
`jerk_window_and_ratelimiter_source.py` / `f7_envelope_acceptance.py` / `shadow_margin_report.py` は
**dt をデータから逐次算出しており最も安全**。
**残る危険は `--fixed_timestep 0.05` という宣言値そのもの**と、それを信じる新しい器具である。

### 4.5 M-30（横ずれ量）に使う量 — **確定**

境界越えフレーム（`f7_realwheel_rerun_jerk0/f7_realwheel_basic.jsonl` line 756、t=7.56、`lane -3→-2`）の
**前後 20 フレームで 1 フレーム差分を実測**して順位付けした。

| 候補 | 定常時の Δ/frame | **境界フレームの Δ** | 判定 |
| :--- | ---: | ---: | :--- |
| `ego.offset` | +0.0185〜+0.0191 | **−3.555915** | **❌ 飛ぶ** |
| `front_bumper.offset` | 同程度 | **−3.555742**（0.25 s 早く） | **❌ 飛ぶ** |
| `front_bumper.t` | +0.0197〜+0.0201 | +0.019708 | ✅ 連続だが下記の偏り |
| **候補 C: `center_t(lane) + ego.offset`** | +0.0184〜+0.0191 | **+0.019085** | **✅ 連続。採用** |

**採用: 候補 C**（車線中心の絶対 t を車線幅テーブルから求め、`ego.offset` を足す）。

* **依存ゼロ** — 今あるテレメトリだけで作れる。新しい出力も DLL 配線も要らない。
* **独立検算が一致** — `e6mini.xodr` から積んだ隣接車線中心間距離 **3.575 m** が、
  `resume_ride_feel.py:1760` に既にあるハードコード定数と**厳密一致**した。
* **絶対値の裏取り** — `lane=-3`, `offset=0` のとき `t=−8.00` がログの実測値と一致。

**候補 A（`front_bumper.t`）を採らない理由**: 連続ではあるが、ego 原点との差が
**旋回中に変動する**（この 0.4 秒窓で 0.4667 → 0.4926 → 0.4901、幅 0.026 m）。
ヨー角変化 Δh=0.00596 rad × 3.92 m ≈ 0.0234 m とほぼ整合する曲率由来のリード誤差で、
**定数バイアスではない**。**F7 が測りたい「介入直後の急な補正」局面でこそ誤差が増える** — §6 T11 の型。

**候補 B（`esminiRMLib` で解析側から再投影）**: 一般性は最も高く junction 越えにも理論上耐える。
`GT_esmini/scripts/rm_lib.py` の `EsminiRMLib` で実現可能（xodr だけで `Init` でき、シム実行不要）。
**ただし現状どの headless スクリプトも使っておらず配線が要る。候補 C の前提が崩れる場面の
クロスチェック／フォールバックとして推奨。**

#### 候補 C の射程 — **検証済み（V14）。シナリオによって成否が分かれる**

`fabriksgatan_traffic_lights.xodr`（`right_turn` / `tljunction` が使う）を直読して確認した。

| 前提 | `e6mini.xodr`（basic） | `fabriksgatan_traffic_lights.xodr` |
| :--- | :--- | :--- |
| 単一 laneSection | ✅ road 0 が全長 1464 m で 1 区間 | ✅ **全 16 road が 1 区間** |
| 車線幅一定 | ✅ | ✅ **全 44 width 要素が b=c=d=0**（幅は 3.5 / 2.0 / 0.3 の 3 種） |
| **`laneOffset`（基準線の横シフト）** | ✅ **要素が 1 つも無い** | ❌ **16 要素。うち 12 本のジャンクション路すべてが `a=1.75`**（通常路 0-3 は 0） |

**走行が実際に道路をまたぐか**（既存 jsonl の `ego.track` を直読）:

| 走行 | 通る road | 判定 |
| :--- | :--- | :--- |
| **basic** | **track 0 のみ** | **✅ 候補 C 成立** |
| **right_turn** | **track 2 → 13 → 3** | **❌ 成立しない** |
| **tljunction** | **track 2 → 13 → 3** | **❌ 成立しない** |

**`track 13` はジャンクション路で `laneOffset=1.75`。** さらに両走行で `ego.lane` が **+1 と −1 に符号反転**する
（基準線の反対側へ移る＝`Lane2Track` の `SIGN(lane_id)` により符号規約自体が変わる）。

**結論**:

* **`basic` では候補 C をそのまま使う。**（`e6mini.xodr` に `laneOffset` が無いので、§4.5 冒頭の実測検証がそのまま有効）
* **`right_turn` / `tljunction` では候補 C を使わない。** 道路遷移で基準線そのものが変わり、
  `laneOffset` が 0 → 1.75 → 0 と飛び、lane 符号も反転する。**3 つの不連続が重なる。**
* **候補 B（`esminiRMLib` 再投影）も、そのままでは解にならない** — `t` は常に道路相対なので、
  道路をまたぐ量としては同じ問題を持つ。

> **ジャンクションをまたぐ走行のための測定量（要設計・M-30b）**
> **世界座標 XY における、ルート車線中心のポリラインからの符号付き垂直距離**を使う。
> ポリラインが道路をまたいで連続である限り、**構成上、基準の張り替えが起きない。**
> 必要な入力は `ego.x` / `ego.y`（既存）と、ルート車線中心のポリライン（`esminiRMLib` または
> 基準走行の記録から生成）。**J4 を右左折系へ広げるならこれを設計してから。**

> **⚠ 合流軌道ワーカーへの申し送り（最優先事項に直接効く）**
> 復帰時にルート車線へ戻す合流を生成するなら、その「横ずれ量」を
> **`ego.offset` でも、車線幅を積んだ `center_t` でも測ってはならない。**
> 直進路（basic 系）なら候補 C で足りるが、**交差点を含む経路では上の 3 つの不連続を踏む。**
> 合流の**評価**にも**生成の入力**にも同じ量が要るはずなので、ここは先に決めたほうがよい。

> **付随して見つかった記録の欠落**: **どの xodr を使ったかは jsonl に記録されていない。**
> 対応する `.log` の `Loaded OpenDRIVE:` 行からしか分からない。
> **jsonl だけを渡された分析者は、候補 C の前提が成立するかを判定できない。**
> 走行メタデータ（xodr パス・dt 体制・config ハッシュ・DLL タイムスタンプ）を
> jsonl の先頭行に出すことを要求仕様に加える（§7 欠損 7）。

### 5.1 V1 の具体手順（掃引で「指定値が効いた」ことを示す）

**背景**: config ローダーは**キーが JSON に存在しなければ警告も出さず既定値を保持する**
（`VirtualDriverConfig.cpp:179-182` の `WarnIfWrongType` が `if (!root.Find(key)) return;`）。
さらに `ad_steering_envelope_*` はどのログにも出力されない。
**したがって「注入が失敗して既定値に落ちた」と「意図して既定値にした」が区別できない。**
これは `--speed` の XPath 不具合と同型の穴である。

| セル | 一次証拠 | 強度 |
| :--- | :--- | :--- |
| **cap ≠ 0**（10 / 25 / 50） | `steer_jerk_active=true` のフレームで、**実現躍度 `\|jerk(steer_out)\|` がその値ちょうどにピン留めされる**ことを確認する | **強**。発火率だけでは値の取り違え（10 と 25 のフォルダ入れ替え等）を検出できないが、**実現躍度の大きさは値ごとに違うので取り違えも検出できる** |
| **cap = 0** | **原理的に上の方法が使えない**（ゼロにはピン留め先の大きさが無い）。`steer_jerk_active` は構造的に常に false（`AdSteeringEnvelope.cpp:97` のガード） | **無い** |

**cap=0 セルに積極証拠を持たせる手立て（要求仕様。本計画では実装しない）**:
1. **config 読み込み直後に `ad_envelope_cfg_` の値を 1 回 LOG_INFO で出す**（現在このログは存在しない）。最小の追加で最も効く。
2. ハーネス側で、注入した JSON を読み返して意図値と一致するか確認する（プロセス外の弱い保証。C++ 側の読み込み成否は保証しない）。
3. config キーを意図的に欠落・型違反させた**陰性対照**を用意し、それが検出可能であることを恒久テスト化する。

**当面の運用**: 1. が入るまで、**cap=0 セルは「到達確認なし」と明記して報告する。**

### 5.2 V12 の具体手順（旧 4 桁計器で取られたログの判別）

**桁数を数える素朴な検査は、捕捉経路によって成立したりしなかったりする。**

* **ネイティブ直捕捉**（`GT_VD_TELEMETRY_JSONL` → `fwrite`。実機/FFB プローブ系）: 生文字列がそのまま残るので**桁数を数えるだけでよい**。
* **`gt_sim_test.py` 経由**（回帰ベースライン・カタログ系）: `json.loads` → `json.dumps` で再直列化されるため**表記は失われる**。ただし **値は保存される**（`json.dumps` は最短往復表現で、値そのものは変えない）。

**したがって値ベースの検査を使う**:

1. 対象ファイルから複数フレームを抽出する。**加減速・操舵が起きている区間を選ぶ。**
2. 候補フィールド: `ego.x`, `ego.y`, `ego.speed`, `ego.h`, `driver.steer`, `envelope.steer_in`/`steer_out`,
   `ffb.gates.residual`/`shadow_norm`/`actual_norm`（FFB 稼働中のみ）。
3. 各値 v について `frac = |v/1e-4 − round(v/1e-4)|` を計算する。
4. **複数フィールド × 複数フレームの多数決**で判定する。
   * 大半が `frac < 1e-6` → **旧（4 桁）**
   * 大半が `frac` が 0.01〜0.5 のオーダーでばらつく → **新（9 桁）**
   * **単一フィールド・単一フレームでは判定しない。**

**実データでの検証済みの例**:
旧 `x=31.2486` → `/1e-4 = 312486`（整数、誤差 1e-10 未満） /
新 `x=31.248626172` → `/1e-4 = 312486.26172`（整数から 0.26 ずれ）。

**使ってはならないもの（実データで確認済み）**:
* **`sim_time` は使わない。** dt が丸い小数なので新計器でも 1e-4 格子の近くに留まり、判別のグレーゾーンに入る。
* **直線走行・横移動ゼロの区間の `y` / `t` / `offset` は使わない。** 新旧とも同じ値になり無情報。
* `preview.dt`（config の echo）、`policy.detail[]`（**常に `%.3f`**、精度の起源が別）は対象外。

## 6. 危険型カタログ

今日の 8 件を一般化したもの。**新しい器具を作るときは、この 9 型それぞれについて「この器具はこの型に対して安全か」を答えること。**

| 型 | 名前 | 今日の実例 | 一般形 | 正常区間では正しく見えるか |
| :--- | :--- | :--- | :--- | :---: |
| **T1** | **指定が届いていない** | `--speed` の XPath 誤りで常に 15 m/s 固定 | 掃引パラメータが対象へ届かず、全セルが同一条件 | ○ |
| **T2** | **計器の底** | 4 桁固定小数 → 躍度量子 1.0 /s² | 分解能が対象の代表値より粗く、分布が量子に張り付く | ○ |

| **T12** | **検出しても合否に乗らない** | `jerk_cap_binding_check.py` / `residual_vs_jerkcap.py` の **kappa 超過検査は、超過を検出しても印字するだけで exit code に一切影響しない**（致命ゲートは cap=0 発火率のみ）。標準出力の文字列まで読まないと気づけない | 検査は動き、異常も検出しているのに、その結果が判定へ伝播しない | ○（**常に緑に見える**） |

**観察**:
* T1/T3/T6/T7/T8 は「肝心な区間だけ間違う」型。**正常区間での一致を確認しても検定にならない。**
* **T6 と T7 は同族** — 値ではなく、値がどの瞬間のものかを取り違える。
* **T8 はその空間版** — 値がどの基準に属するかを取り違える。
* **T9 と T12 が最も危険**: 他の型は間違った数値を出すが、この 2 つは**検証したという事実自体が嘘になる**。
  T9 は検査が走らない、T12 は検査が走って異常を見つけたのに判定へ伝わらない。
  **どちらも「ゲートが緑だった」という報告を無意味にする。**
* **T9 の系統的な形**: ほぼ全ての分析スクリプトがテレメトリを `dict.get(key, 0.0)` / `.get(key, False)` で読む
  （`shadow_margin_report.py:84-96`, `residual_decompose.py:81-86`, `worst_case_conditions.py:107-138`,
  `jerk_window_and_ratelimiter_source.py:126-141`, `wheel_session_report.py:82-88`）。
  既定値が**「正常に見える値」**なので、フィールド名が変わる・消えると `KeyError` で落ちず
  **「何も起きなかった」という統計を静かに作る。** 本セッションだけでフィールドの改名・意味変更が
  複数回起きている（`09ef973f` の残差方式全面置換、`f78f60f8` の `effective_force` 意味論変更）。
  **この規律に従っているのは新規プローブ `vd_lane_offset_semantics_probe.py` の
  `_preflight_instrument_check()` だけ。他へ波及させること。**
* **T11 は T1〜T9 のメタ版**: 「正常区間では正しく、肝心な区間で間違う」という今日の 4 件の性質を、**検証手法の側が持っている**。
  検証手法を設計したら、**その手法自身が肝心な区間を覆えるか**を必ず問うこと。
* 撤回された 1.0078 倍が疑われにくかったのは「わずかに超えている」というもっともらしい大きさだったから。
  **3.58 倍なら誰でも疑うが、0.78% 超は受け入れられてしまう。**

### 8.5 しきい値掃引 45 走行の偽ラッチ 9 件（**本計画で新たに確定**）

`test_results/f7_thr_sweep_summary.txt` を直読して確定した。**しきい値の水準決定に直結するので詳述する。**

**9 走行が「t=0.01 s（第 1 フレーム）に、残差 0.00000 で、`moving` フレーム 0 のままラッチ」している。**

| thr | 偽ラッチした走行 |
| ---: | :--- |
| 0.050 | r1 right_turn / r2 right_turn / r3 basic |
| 0.040 | r1 right_turn / r2 right_turn / r3 right_turn |
| 0.035 | r1 right_turn / r2 right_turn / r3 right_turn |

**残差 0 でラッチすることは、残差方式の機序上あり得ない。** 別の経路で MANUAL に落ちている。

**決定的な診断 — `block_reason` の内訳**:
```
below_residual  81801
inactive        38115
none              138
bootstrap          36     ← 45 走行あるのに 36 しかない。差はちょうど 9
```
1 走行につき `bootstrap` が 1 フレーム出るはずが **36 しかなく、不足はちょうど 9**。
**偽ラッチした 9 走行は、シャドウがブートストラップする前に MANUAL へ落ちている。**
残差検出器はまだ初期化されておらず、**この 9 件のラッチは残差方式とは無関係**である。
（原因は未特定。起動時のホイール非中立・ボタン状態・前走行の状態残りなどが候補。**要調査**）

**掃引の読み方が変わる**:

| thr | 報告されたラッチ率 | **偽ラッチを除いた真のラッチ率** |
| ---: | :---: | :---: |
| 0.080 | 0/9 | **0/9** |
| 0.060 | 1/9 | **1/9** |
| 0.050 | 6/9 | **3/9** |
| 0.040 | 6/9 | **3/9** |
| 0.035 | 5/9 | **2/9** |

**thr ≤ 0.05 のラッチ率はおよそ半分になる。** 「0.05 で 6/9」は実際には 3/9 である。

さらに悪いことに、**偽ラッチ 9 件はすべて thr ≤ 0.05 に集中している**。
掃引は時間順が閾値順と一致しているので（T10）、**「しきい値を下げたから増えた」と
「セッション後半でホイールが噛まなくなったから増えた」が分離できない。**
実際、偽ラッチ走行はすべて `moving` フレームが 0 ＝ **ホイールが一度も動いていない**。
これは閾値の効果ではなく**機材が噛んでいない**兆候である。

> **結論**: この掃引は「しきい値を下げると誤ラッチが増える**向き**」の弱い傍証にはなるが、
> **どの水準にすべきかの根拠には使えない。** 偽ラッチの原因を特定し、順序をランダム化して
> 取り直すまで、J1 の水準決定は **M-01/M-02/M-04/M-05 の直接測定**に依る。

> ### 【2026-07-28 追記】J1 掃引を根拠として**正式に撤回する**
>
> 上の訂正（6/9 → 実質 3/9）に加えて、**この掃引は再現できない**ことが確認された。
> **掃引を駆動したドライバスクリプトがリポジトリに存在しない**
> （`test_results/f7_thr_sweep/thr*_r*/` の出力だけが残っている)。
>
> 出所を辿れない数値は未測定として扱う、というのがこのプロジェクトの規律である。
> したがって:
>
> * **J1 掃引に由来するしきい値の根拠は撤回する。** 上の表は「かつてこう報告された」
>   という記録としてのみ残し、**水準決定の根拠には一切使わない**。
>   本文中の `6/9` を根拠として引用してはならない。
> * **取り直しは、駆動スクリプトを書き直してからでなければ意味がない**
>   （偽ラッチ 9 件の原因特定と順序のランダム化も同時に必要 — 上記のとおり）。
> * **出荷値には影響しない。** `override_residual_threshold = 0.08` の根拠は
>   この掃引ではなく、`ManualDriveConfig.hpp` に書かれた物理的な議論である
>   （SDL2 量子化 ~0.001・機械ジッタ ~0.005 の床より十分上、かつ飽和した 0.6 の
>   サーボ力に抗して握られたホイールなら ~1.0 axis-frac/s で発散するので
>   80 ms で 0.08 を超える）。**撤回によって変わる出荷パラメータは無い。**

**これは本計画の使い方の実例でもある**: 45 走行という規模と「事前固定の停止規則」という
手続きの正しさが、**中身の 20% が別経路の偽陽性である**ことを覆い隠していた。

### 9.1 `find_episodes()` の検証設計（V3 / V8 の具体化）

介入区間の切り出しは J1 の M-05 と J5 の M-41/M-42 の土台であり、**今日の不具合 3 件目と同じ型の急所**。

**(1) 陰性対照 — 既存ログで今すぐ回せる**

**手放し＝人の介入ゼロが既知**。期待値は `find_episodes()` が**空リストを返す**こと。

> として扱う（`wheel_session_report.py:236-238`）。**この対照では器具自身の合否文言を信用せず、
> 「0 件だったこと」自体を PASS 条件として外側で判定すること。**

**(2) 陽性対照・境界精度 — 製品自身をオラクルにする（新規フィクスチャ不要）**
`override.manual_transition` / `override.auto_transition` は製品 `OverrideManager` が毎フレーム出す、
`wheel_session_report.py` とは**独立した一次情報源**。これを正解として使う。

| # | 検査 | 何を捕まえるか |
| :-- | :--- | :--- |
| (i) | すべての `manual_transition=true` の時刻が、いずれかのエピソード区間 `[start, end]` に含まれる | **見逃し（致命）** |

§8 の分類（検定済み / 要検定 / 撤回済み）は**既存の記録を読んで付けたもの**であり、
✅ が付いた数値も**本計画の検定を通したわけではない**（既存の裏付けの質で分類した）。
**§9 の 1〜7g を実施してはじめて、器具は「検定済み」になる。**
