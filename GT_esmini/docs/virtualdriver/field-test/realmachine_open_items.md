### 前提B': FFB の力の出し方を変えた（デッドマン方式）— **実機で触感を確認していない**

* **何を変えたか**: 全エフェクトを **`SDL_HAPTIC_INFINITY`（無期限）から有限長へ**変え、
  毎周期 `SDL_HapticUpdateEffect` + `SDL_HapticRunEffect` で**張り直す**方式にした
  （前提B を構造的に消すため。下記参照）。
* **なぜ確認が要るか**: **力の出し方そのものを触ったので、触感が変わりうる。**
  窓が短すぎれば張り直しが間に合わず**力が途切れてガタつく**。
  ヘッドレスには FFB デバイスが無いので、**この判定は実機でしかできない**。
* **確かめること**: 普通に走って、**以前と比べてハンドルの手応えがガサついていないか**。
  特に**保舵中（力が一定のとき）に細かい振動やカクつきが出ていないか**。
* **窓の決め方（実装）**: 固定値ではなく `clamp(観測更新間隔 × 3, 20 ms, 250 ms)`。
  更新間隔は**実測**（毎フレームの `dt` の減衰最大値）だが、
  **係数 3 と上下限 20/250 ms は設計値であって実測ではない**——
  ガタつきの閾値は実機でしか測れないため。
* **1 周期落ちてもガタつかない根拠（設計論・未実測）**: 窓は更新間隔の 3 倍なので、
  1 回落としてもまだ 2 周期ぶん残る。**3 回連続で落として初めて力が切れる。**
  張り直しは `attack_length = fade_length = 0` なので**立ち上がりの傾斜が無く**、
  再始動しても力の値は連続する（クリック音や段差が出ない設計）。
* **既知の弱点（正直に）**: 窓はシミュレーションの `dt` から算出している。
  ホイールを繋ぐ構成では esmini がリアルタイムで走るので `dt` は実時間に追随し、
  この算出は妥当である。**ただしシミュレーションが一時的にストールして
  実時間の間隔が `dt × 3` を超えると、その瞬間だけ力が切れうる。**
  ここが実機で最初に出るとしたらこの形（重いシーンでの一瞬の抜け）。
* **状態**: **実機未確認。** ガタついたら窓を広げる（上限 250 ms まで）か、
  `dt` ではなく実時間（`SDL_GetTicks`）で測るように変える。

### 前提B: プロセスを強制終了すると、サーボが力を出したまま固まりうる

* **何が問題か**: 正常終了（QUIT）とシグナル/SEH クラッシュには解放処理があるが、
  **ハードキル（`taskkill /F /T`）ではユーザーモードの解放ハンドラが一切走らない**。
  `SDLFFBSink.cpp` の emergency release（atexit/シグナル/SEH）は、
  **OS がプロセスを外から殺す経路では原理的に発火しない**。
* **現存する経路**: `GT_esmini/web/backend/services/simulation_runner.py` に
  `taskkill /F /T` へエスカレーションするフォールバックがある
  （正常停止を先に試み、タイムアウト後にのみ使う設計）。
* **証拠の強さ**: **コード読解のみ。実機で再現も否定もされていない。**
* **実機で確かめること**: FFB が効いている状態で `taskkill /F /T` を実行し、
  **ホイールに力が残るか**を確認する。**残る場合、電源を抜く以外に解除手段が無い**ので、
  必ず**手を離した状態**で行い、電源スイッチに手が届く位置で実施すること。
* **状態: 「未知」から「設計で上界が言える・ただし1点だけ実機確認が要る」へ降格した**
  （完全な降格はしない。理由は下記）。

#### 降格の根拠と、それでも残る 1 点

デッドマン方式（`543ced58`）により**上界が計算できる**:

| 問い | 答え |
| :--- | :--- |
| 窓の長さ | **固定値ではない**。`clamp(観測更新間隔 × 3, 20 ms, 250 ms)` |
| 100 Hz（既定）で | 10 ms × 3 = **30 ms** |
| 250 Hz なら | 4 ms × 3 = 12 ms → 下限に当たり **20 ms** |
| 50 Hz なら | 20 ms × 3 = **60 ms** |
| **キル後に力が消えるまでの上界** | **最後の張り直しから 1 窓以内 ⇒ どんな設定でも 250 ms 以内**（clamp が効くため） |

**「既定 100 Hz → 30 ms」は平常時だけの数字である**（監査が算術を検算して指摘）。
窓の入力は `dt` の**減衰する最大値**（毎フレーム `×0.995`）なので、
**1 秒の単発スパイクが 1 回起きると、そのあと約 5 秒間は窓が上限 250 ms に張り付く**
（1000 ms から 250/3 ≒ 83 ms まで減衰するのに 0.995^n が必要な回数 ≒ 約 5 秒）。
つまり**重いシーンやアプリの一時停止の直後にキルすると、上界は 30 ms ではなく 250 ms** になる。

* 安全側の性質: **上界は必ず 250 ms 以内**という保証は崩れない。
* 代償: スパイク直後は解放が最大 8 倍遅い。**それでも「永久」ではない。**
* 減衰を速めれば張り付きは短くなるが、そのぶん**力が途切れるリスクが上がる**
  （窓が実際の間隔に追いつけなくなる）。**このトレードオフは実機の触感を見て決めるべきで、
  机上で動かすべきではない。**

**⇒ 条件B の「永久に力が残る」は設計上ありえなくなった。** これが降格の根拠である。

**それでも実機確認を 1 点だけ残す理由**: 上界は
**「デバイスがエフェクトの `length` を仕様どおり守る」**ことに依存する。
これは DirectInput / SDL の**文書化された API 契約**であり、
`IRP_MJ_CLEANUP` の挙動（**仕様に無く、ベンダにしか分からない**）とは
証拠の強さが桁違いだが、**この個体で確かめてはいない**。

* **実機で見るのはこれだけ**: FFB が効いている状態で `taskkill /F /T` し、
  **1 秒以内に力が消えるか**。手を離した状態で、電源に手が届く位置で行う。
* 消えれば条件Bは閉じる。消えなければ、ドライバが duration を無視しているということなので
  **その事実自体が重要な発見**（他の対策——別プロセス監視等——へ切り替える根拠になる）。

## なぜ「この3件だけ」なのか（根拠）

**判定基準**: ヘッドレスで答えが出ない項目とは、
**「合成プラントが私の書いたモデルである」ことが原理的な障害になる**もの、
または**人体・ハードウェアの物性そのもの**を問うものに限る。
それ以外は実機に回さずヘッドレスで詰めた（下の表）。

この基準が空論でないことは、**較正の自動化を実際に試して失敗した**ことで裏づけられた
（`test_results/f7_fleet_autocal2.log`）。
プラントのばらつきに対する頑健性を、合成データだけを見ながらコードで解こうとすると、
**誤検知は消えたが本物の検出が 16/18 → 12/18 へ落ちた**。
**モデルの誤差を、そのモデルの中だけで較正することはできない。**
だから R-1（実機の無負荷軌跡）が要る——これは代替の効かない一次証拠である。

## R-1. 手を離したホイールの「無負荷軌跡」【最重要】

**やること**: AD に運転させたまま、**ハンドルに一切触れず**、カーブを含む区間を1分ほど走る。

**なぜ実機でないと駄目か**: 検出器は「この力なら手が無いときホイールはどこにいるか」を
モデルで予測し、実測との差を手の証拠とみなします。**その予測が実物とどれだけ合うかは、
実物でしか測れません。**（現在の合成プラントは検出器と同じ定数を使っているので、
そこでは差がゼロになるのが当たり前で、何も検証できていません。）

**判定**: 走行後 `telemetry.jsonl` の `ffb.gates.residual` の最大値を見ます。
**しきい値 0.08 に対してどれだけ余裕があるか**が答えです（ラッチしたかどうかではなく）。

### R-1b. ついでに `v_max` を確定させる【追加・重要】

**なぜ**: 検出器の中核定数 `v_max = 1.0 axis-frac/s` は、**測定値ではなく外挿**です。
2026-07-25 の力速度表は **f=0.58 で 0.954 /s が最大**（サーボの力上限が 0.6 なので
そこで頭打ち）で、**1.0 に到達したサンプルは 1 つもありません**。
1.0 は飽和漸近線の当てはめ値です。これがずれていると、
**速い個体では誤検知・遅い個体では検出漏れ**として出ます（18 変種のフリートで実測済み）。

**やること（2 分・AD は動かさない）**:

```powershell
# ハンドルから手を離してください。ホイールが自分で回ります。
scripts\ffb_spike\.venv\Scripts\python.exe scripts\ffb_spike\07_friction_map.py --part fv --yes
```

**何を見るか**: 出力の力→速度の表で、**力を上げても速度が頭打ちになる点**があるか。

| 観測 | 意味 | すること |
| :--- | :--- | :--- |
| 0.58 付近でまだ速度が**伸びている** | **飽和点に届いていない**＝ v_max は測れていない（今と同じ状態） | 下の「力が足りない場合」へ |
| 速度が**明確に頭打ち**になる | **そこが v_max**。実測値が得られた | その値を `override_shadow_v_max` に入れる |

**力が足りない場合（今回もそうなる可能性が高い）**: サーボの `max_force` が 0.6 に
制限されているため、この装置では飽和点まで押せない可能性があります。その場合は
**「この G29 では飽和点に到達できない」ことが結論**で、それ自体が重要な情報です
（＝ v_max は運用範囲では効いておらず、線形域 `v ≈ 3.35·(|f| − 0.16)` だけが効いている）。
**分かったことをそのまま伝えてください。**「測れなかった」も答えです。

**この確認は R-1 と同じセッションでできます**（どちらもハンドルに触れない）。

## R-2. ハンドルを「握って静止させる」と、置いてあるだけの区別

**やること**: 直線で **(a)** ハンドルに手を置くだけで力を入れず10秒、
**(b)** しっかり握って動かさないように10秒。どちらも**回さない**でください。

**なぜ実機でないと駄目か**: 人の手は完全に静止できるのか、という**ハードウェアと人体の問題**です。
合成プラントは私が「静止」と書けば完全に静止するので、この問いに答えられません。
ここが分かれば、FFB 無しの構成で「置き忘れたハンドル」と「握っている手」を
軸の値だけで区別できるかが決まります（今はできないと仮定して、
**動かした瞬間に検出**する設計にしてあります）。

## R-3. 走行開始時にハンドルが曲がっていた場合の操作感

**やること**: 前の走行でハンドルを **60度ほど回した状態のまま**次の走行を開始し、
そのまま AD に走らせる → その後**ハンドルを少し動かして**操作を取り戻せるか試す。

**なぜ実機でないと駄目か**: 「少し動かせば取り戻せる」で**実用上困らないか**という
ユーザー体験の判断で、これは実機で人が触ってしか分かりません。
（t=0 で即座に手介入と誤判定して AD が一切走らない、という以前の不具合は解消済みです。）

| 制御移管時のサーボ停止 | xosc 通しで `control outputs released` を確認。**回帰ゲートで自動検証** — 当初「同一フレーム内で相殺され telemetry に出ない」と判断したが**測ったら誤り**で、per-domain teardown の後の Activate は ACTIVE→ACTIVE 扱いで `SetUpControlOutputs()` を再実行しないため `vd_active` は false のまま残る（t=8.10 以降 400 フレーム）。matcher 追加済み |
| プラント/シャドウ不一致の影響 | 18変種で分布取得。`v_max` 一致なら余裕3〜4倍、速すぎると誤検知 ← **R-1 はこの校正の一次証拠** |
| 較正の自動化（G29 以外のハンコン対応） | **実装して測って、不採用にした**。誤検知は 6/18 → 0/18 になったが、**本物の検出が 16/18 → 12/18 に落ち**、校正が合っている個体の余裕も 0.24→0.97 倍へ悪化。**採用しない**（詳細は progress §8） |

### 実機を待たずに次に試せること（R-1 の結果が出る前でも着手可）

自動較正そのものは筋が悪くない。失敗したのは**推定器と学習窓**である:

* 推定器が**最大値**だったので、プラントノイズがそのまま上振れとして入る。分位点にすべき。
* 学習窓を「手の証拠が無いフレーム」まで広げたため、**遅いフレームばかり拾って
  `v_max` を過小推定**し、握られたホイールに対してシャドウが動かなくなった（＝検出漏れ）。
* **筋の良い方向**: 走行中に推定するのをやめ、**起動時の専用較正フェーズ**にする。
  「3秒間ハンドルから手を離してください」と表示して既知の力を掃引すれば、
  **手が乗っているかを推定する必要が消える**（今回の失敗はすべてこの循環から出ている）。
  R-2 の結果（人の手が完全静止できるか）は、この画面設計にも効く。

### R-4. ペダル軸のキャリブレーションとキックダウン閾値の関係

**やること**: 実機 G29 のアクセルペダルを、デッドゾーン・軸較正込みでどこまで踏み込めるか
（正規化スロットル軸の実測最大値）を測る。

**なぜ実機でないと駄目か**: `adas_kickdown_threshold`（既定 0.95）は正規化スロットル軸との
比較で判定する。`ScriptedInputSource` は常に厳密に 1.0 を出せるが、実機ペダルはデッドゾーンと
軸較正を経た後、0.95 に一度も到達しない個体がありうる。もしそうなら、AEB 抑制
（REQ-AD-025 段d）と MSL 一時解除（REQ-AD-030 段b）は、**全ての合成テストが緑のまま**
実機ペダルでは物理的に到達不能になりうる——合成入力プロファイルは軸較正を経由しないため、
ヘッドレスでは原理的に検出できない齟齬である。

**すること**: 実機ペダルの到達可能な正規化最大値を測り、そこから閾値を較正する。

**状態**: 未実施。

### R-5. AEB介入中のFFB触感の変化

**やること**: ADAS（AEB）が急制動で介入している最中に、ハンドルの手応え
（自己整合トルク・摩擦・ダンパー、いずれも速度スケール: `ffb.sat_gain` /
`friction_speed_gain` / `damper_speed_gain` / `assist_low_speed` / `assist_high_speed`）
がどう変わるかを主観で確認する。

**なぜ実機でないと駄目か**: ADAS フックは物理ステップと FFB 更新より前で走るため、ハンドルは
「調停後（ADAS介入を含む）」のブレーキ・速度を物理的に正しく感じる——設計上は妥当だが、
この触感変化を**観測する仕組みが現状どこにも無い**。唐突・誤解を招く触感でないかは
主観評価そのものであり、合成データでは原理的に判定できない。

**すること**: 緊急制動介入の最中・直後にハンドルの手応えが唐突・誤解を招く変化をしないか、
実機で確認する。

**状態**: 未実施。

### R-6. OverrideManager 残差検出器とAEB介入の相互作用

**やること**: `ffb.target_track.enabled`（既定 false）を true にしてサーボを有効化した上で、
AEB が実際に発火する構成（`10_manualdrive_adas/` の unresponsive 系相当）を、**手を離した状態**
で走らせる。

**なぜ実機でないと駄目か**: AEB 介入で速度が変わる → 速度スケールの FFB 各項が変わる →
指令力が変わる → シャドウ予測も同じ力を見るので、残差は理論上ゼロ近傍に留まるはずである。
だがこれは**論証であって実測ではない**——デフォルト off の split 構成で servo を有効にした
場合の実際の挙動は、実機の無負荷軌跡でしか確かめられない（R-1 と同じ理由）。

**すること**: 手を離したまま AEB 介入イベントを経験させ、`ffb.gates.residual` が誤って
MANUAL ラッチしないことを確認する。

**状態**: 未実施。

### R-7. LKA 補正の FFB 反力伝達（req-vd-ad:REQ-AD-027 段d）

**やること**: `adas_lka_enabled` を true にし、緩やかに車線から外れていく状況を作って、
LKA の補正操舵が**実ハンドルの反力として手に届くか**を主観で確認する。

**なぜ実機でないと駄目か**: 補正が `cmd.steering` に乗ることは自動で示せる（フェーズDの
`md_lka_drift` が `gt.lka.correction` として測っており、E2E も緑）。だが段d が問うているのは
その先——それが実デバイスのトルクとして**手に届くか**であり、headless の plant モデルには
届く先が無い。R-1/R-5 と同じ理由で、合成データからは原理的に判定できない。

**補正の大きさの見当**: `adas_lka_correction_max` は 0.03（正規化操舵）で、通常出るのは
0.004 前後。G29 の 900° レンジに対して 0.004 は約 3.6°、上限でも約 27° である。
**手応えとして感じられる下限を下回っている可能性がある**——これは値を上げれば解決する
という話ではなく（上限は「人間が常に上回れる」ことが要件）、補正の**提示**を反力そのもの
ではなく別チャネル（FFB パルス等、設計 §7 の拡張オプション）でやるべきか、という設計判断に
つながる。実機で「何も感じない」が観測されたらそれは失敗ではなく、この判断の入力である。

**すること**: 補正が入っている間の手応えを主観評価し、(1) 感じ取れるか (2) 車線内へ戻す
方向として自然か (3) 唐突でないか を記録する。

**状態**: 未実施。

### R-8. 人間操舵優先の入力レート閾値が実ハンドルのジッタで誤発火しないか

**やること**: `adas_lka_enabled` を true にし、**ハンドルに手を置いたまま動かさず**直進走行し、
`gt.lka.suppressed_steer` が立たないことを確認する。次に意図的な操舵をして立つことを確認する。

**なぜ実機でないと駄目か、そしてこれが最も差し迫った項目である理由**: LKA の人間操舵優先は
入力**レート**（`adas_lka_steer_override_rate`、既定 0.03 /s）で検出する。自動ゲートは
ScriptedInputSource の区分線形プロファイルを再生するのでノイズがゼロだが、実 G29 のコラム
ジッタは約 0.005 axis（`scripts/ffb_spike/CHARACTERIZATION.md`）で、dt=0.05 では見かけのレート
**約 0.1 /s** ——**閾値の3倍以上**になる。つまり実機では、**運転者が何もしていないのに
抑制が立ちっぱなしになり、LKA が一度も作動しない**可能性が高い。

**根拠は実装コードのコメントに書いてある**（本項はその要約ではなく、そこから起票した
実機作業項目である）:

| 根拠 | 場所 |
| :--- | :--- |
| ジッタ ~0.005 axis → dt=0.05 で見かけ ~0.1 /s ＝閾値超、合成データからは対処を選べない | `GT_esmini/include/gt_esmini/control/manualdrive/LaneKeepAssist.hpp` の `steer_override_rate` 直上のコメント（"REQUIRES CALIBRATION, AND SPECIFICALLY ON A REAL WHEEL" の段） |
| レート＋ホールドは本来トルクで測るべき量の headless 代用である | 同ヘッダの `steer_override_hold_s` 直上のコメント |
| ジッタ 0.005 axis の実測出所 | `scripts/ffb_spike/CHARACTERIZATION.md` |
| 通常の車線変更の入力レート ≈ 0.01 /s（閾値との余裕が3倍しかないこと） | 同ヘッダの `steer_override_rate` コメント前半／設計書 §12 の閾値表 |

自動ゲートはこれを構造的に見られない（合成入力にジッタが無いのだから）。
`GT_esmini/scripts/verification/test_manualdrive_matchers.py` も
`test_LaneKeepAssist.cpp` も緑のまま、実機でだけ機能が死ぬ形になる。

**対処の選択肢（実測してから選ぶ）**: (a) 閾値を上げる——ただし通常の車線変更の入力レートが
約 0.01 /s なので、上げすぎると今度は本物の操舵を見逃す。可動域は狭い。
(b) 差分を取る前に入力を平滑化する。(c) レートではなく**トルク**で検出する（本来こちらが
正しい量で、レート＋ホールドはそれが取れない headless での代用である——`LaneKeepAssist.hpp`
の `steer_override_hold_s` の注記を参照）。

**すること**: 手を置いたまま静止した状態での `gt.lka.suppressed_steer` の発火率と、
そのときの実測入力レート分布を記録する。上の3案のどれを採るかはその数字で決める。

**状態**: 未実施。
