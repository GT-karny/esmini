## 2. 戦略的な発見(テーマ横断)

45提案を束ねると、GT_esminiの進化軸は7本に整理できる:

1. **検証工場の「評価語彙」拡張** — TTC/PET/必要減速度などのサロゲート安全指標と衝突検出が検証系に存在しない。ISO 34502系の議論とF2(ギャップ受容)の安全マージン評価の土台。**全テーマ中で最も費用対効果が高い**(C++改変ゼロ、scene.jsonl後処理のみ)
2. **SiL接続プラットフォーム化** — 既存の外部接続(RealDriver UDP/NetworkInputBridge)は全て「非同期・フリーラン・latest-wins」で、SiLに必須のフレーム同期・一時停止・決定論が無い。素材(IInputSource、RegisterController、in-processハーネス)は揃っており増分は小さい
3. **実走行データ輸入路の開通** — rosbag/MDF4/CAN/GNSS取込みがゼロ。一方FollowTrajectory実行系・rm_libマップマッチング素材・xosc生成ファクトリ・注釈レジストリと受け皿は完備。UN-R157/NATMの「実走行データに根差したカバレッジ」要求に直結
4. **sim自体の妥当性立証(credibility)** — フル車両物理を売りにしながら「その物理が実車とどこまで合うか」の証拠生成機構が皆無。CarMaker等との信頼性格差の核心で、仮想試験を安全論証に使う前提条件
5. **実行スケールと資産化** — OSIポート48198ハードコードが並列実行を阻んでおり、カタログ数百本化・F4 CI化の直前に確実に踏むボトルネック。commit_hashは記録されるだけで一切集計されていない
6. **センサー知覚の現実化** — SensorView生成系は実装済みだが外部配信未接続(死蔵)。遮蔽・誤差モデルを足すと「全知GroundTruth」から「現実的な知覚入力」へ
7. **DiL実験装置化/共有・デモ** — 実ハンドル+FFB+フル物理という競合に無い資産を、HMI実験(TOR/反応時間)・教育採点・run共有へ転用する

## 4. Tier 1 詳細

### P4: 実行時刻制御 — ポーズ/コマ送り/条件ブレークポイント(S)

- **誰が**: 制御アルゴリズムのデバッグ担当。検証failの原因調査・VD判断系列の追跡という日常工程
- **何が欠けている**: サブプロセス実行(GT_Sim経由=Web UIの全実行)はフリーラン固定。PAUSE/RESUME/STEP:\<n\>が存在しない。商用シミュレータでは当然の機能の欠落筆頭
- **土台**: GT_Sim --control_pipeの行コマンド機構(main.cpp:220-262にSPEED:/DRIVE_MODE:/QUIT実装済み)、speed変更API(PUT /{job_id}/speed)の完全同型複製で済む
- **設計**: ControlPipeにPAUSE/RESUME/STEP追加(paused時はSE_Step/GT_StepスキップしWS/UDP配信は最終フレーム維持)。backend PUT /api/simulations/{job_id}/playback、LiveMonitorPanelに再生制御ボタン3個。第2段でBREAK_ON:\<expr\>(テレメトリ値・制約種別での自動停止)
- **相乗**: P1(SUT接続)と組むとSUT側デバッガのブレークとシミュレータ側ポーズが両立し「シミュレータが先に進んでしまう」問題が消える

### P11: サロゲート安全指標エンジン(M)

- **誰が**: V&V担当。F2/F3を含むVDポリシー検証と回帰ゲート運用で「ぶつからなかった」だけでなく「どれだけ危なかったか」を定量化
- **何が欠けている**: 既存マッチャは速度・車線・THWパーセンタイル止まり。ISO 34502/SOTIF議論に必須のTTC/PET/必要減速度a_reqの算出・時系列記録・閾値判定が無い
- **設計**: `GT_esmini/scripts/verification/criticality.py` 新設 — scene.jsonl+telemetry.jsonlの後処理でペアワイズTTC/THW/PET/a_reqを算出しcriticality.jsonl出力。_eval_mustへ min_ttc_above / pet_above / required_decel_below / thw_above の4マッチャ追加。LiveSceneViewにTTC色分けレイヤー(LayerKey 1個)
- **C++改変ゼロ**(OSI出力の純粋な後処理、検証Python層は凍結対象外)。expectations.yamlに `min_ttc_above: 1.5` と書くだけで合否化
- **注意**: PETの交差領域定義は道路形状依存 — 第1段はOBB軌跡投影の保守的近似、junction系はmeta.yamlにconflict領域ヒントの逃げ道

### P1: SUTロックステップ接続ゲートウェイ(M)

- **誰が**: 社内ADAS/ADスタック(ACC/AEB/LKA/ALKS)のSiL担当。自社スタックをegoの運転主体としてGT_esminiに接続
- **何が欠けている**: 既存外部接続(RealDriver UDP 53995 / NetworkInputBridge 9100)は全て非同期latest-sample-wins。フレーム同期保証が無くOSスケジューリングで結果が変わる=SiLの決定論要件を満たさない
- **設計**: `ControllerSutBridge`(型id 1003)+LockstepChannel新設。フレームkのOSI GT/HVDをframe_id付き送信→SUTが同frame_idのコマンドを返すまでGT_Stepがブロック→物理1ステップ進行。--no_realtime+ヘッドレスでCIは実時間の数十倍速。参照Pythonクライアント同梱
- **副産物**: 死蔵中のGT_ENABLE_OSI_MOTION_REQUESTスキャフォールド(監査TODO-2で削除判断保留)をMotionRequest入力形式として正式活用 → TODO-2の決着
- **本質的難所**: SUT無応答時の安全フォールバック(前回値ホールドNフレーム→縮退停止)のセマンティクス設計

### P26: 並列ヘッドレスバッチ実行基盤(M)

- **誰が**: 検証担当とF4 CI運用者。カタログ36本→数百本化で逐次forループ(現状数十分)が破綻する直前
- **何が欠けている**: OSI GroundTruthだけ `#define OSI_OUT_PORT 48198`(GT_OSIReporter.cpp:37)でハードコードされ、複数ワーカーが衝突して並列化不能
- **設計**: (1) GT_InitWithArgsに--osi-port追加(--sv-port/--vd-portの前例どおり、GT管理フォークファイル内で完結) (2) gt_sim_test batch()に--workers N、ProcessPoolExecutorで1run=1サブプロセス、ワーカーindexからポートブロック束(48198+idx*16)割当 (3) 親がverdict.jsonをマージし現行形状のbatch_verdict.jsonを出力 → 注釈レジストリ・Web UIは無改修
- **整合**: R5-U4(OSIライト出力ポート)とポート設計を着手時にすり合わせ。既定ポートは不変とし並列時のみオフセット

### P12: 安全エンベロープ不変条件モニタ(M)

- **誰が**: V&V責任者。シナリオ作者がexpectationsを書き忘れても落ちない安全網
- **何が欠けている**: must[]はシナリオ個別記述のみで全run常時適用の安全要件の概念が無い。**衝突検出そのものが検証判定経路に存在しない**
- **設計**: config/global_invariants.yaml(collision_free/road_departure_free+既存must語彙)を全entryへ自動マージ、verdict.jsonにinvariantsセクション分離。collision_freeはscene.jsonlのOBB交差判定(分離軸テスト)。run_regression_gate.ps1に-FailOnInvariant追加(behavioral WARN運用のまま不変条件違反だけ硬いfailに格上げ)
- **注意**: phase3_batchは「ポリシー未実装段階で意図的にFAIL」する設計のため、invariantは物理的絶対条件(衝突等)に限定し快適性系閾値は通常mustへ — 線引きの文書化が必要
